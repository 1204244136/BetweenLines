# 多 AI 协同翻译校对评审体系架构设计规划报告 v2.4（修订版）

> 历史设计稿：保留 v2.4 当时的修订讨论，不作为当前实施契约。当前实现见 [CURRENT_SYSTEM.md](../CURRENT_SYSTEM.md)；修改约束以 [AGENTS.md](../../../AGENTS.md) 及其引用的 [领域契约](../../contracts/) 为准。本文中的流程、配置和实施计划可能已调整。

## 本次修订内容

### P0 修复（与现有 BetweenLines 架构对齐）

1. 不再宣称“彻底淘汰 Temperature”，改为：
   - 推理模型使用 reasoning_effort / thinking budget；
   - 非推理模型继续使用 temperature；
   - 二者互斥，由模型能力自动决定。

2. 单模型人格分化不再假设所有模型支持 OFF 思考。
   - Stage 1 自动选择该模型支持的最低思考档位；
   - Stage 2 选择中档；
   - Stage 3 选择最高档；
   - 兼容 DeepSeek-R1、o 系列、QwQ 等纯推理模型。

3. 备注结构改为与工作台解析协议一致：
   - 分析信息位于“修改结果”之前；
   - 修改结果始终为最后一个字段；
   - 保持与 parseAutomatedNote 契约兼容。

### P1 架构修复

4. 模型能力检测统一复用 model-capabilities.js。
5. 保留低分归因与线上查证两个既有阶段。
6. 双模型模式下取消“自己仲裁自己”，改为匿名独立会话仲裁。
7. 审核统计统一接入现有 status 统计体系。
8. 多 Stage 可绑定独立 AI Preset。

### P2 自洽修复

9. 统一成本评分语义。
10. 统一早停率口径。
11. Token 成本统计拆分：
    - 调用次数；
    - 加权 Token。
12. 删除无数据支撑的提升百分比描述。

## 新版核心原则

### 原则一：模型能力优先

永远根据 detectModelCapabilities() 的结果决定：

- 是否支持 reasoning；
- 支持哪些 reasoning 档位；
- 是否允许 temperature；
- 是否需要 Claude Thinking Budget。

禁止再通过模型名称硬编码判断协议。

### 原则二：先发现问题，再润色问题

流程固定为：

确定性规则
→ Stage 1 严格门禁
→ Stage 2 文学复审
→ 低分归因
→ 线上查证
→ Stage 3 仲裁
→ 输出侧门禁
→ 工作台落盘

### 原则三：所有高级阶段都必须可跳过

允许：

- Stage1 → 直接完成；
- Stage1 → Stage2 → 完成；
- 只有存在真实分歧时才进入仲裁。

## 推荐 MVP 范围

- 双模型挑战者模式；
- 单模型人格分化；
- reasoning_effort 控制；
- Fast Pass；
- critique 输出。

Phase 2：

- 动态仲裁；
- 模型画像；
- autoSchedulePipeline；
- 多预设绑定。

Phase 3：

- audit_risk 联动；
- 人工确认反馈学习；
- 自动模型权重校准。

## 结论

v2.4 的核心思想不再是“多模型投票”，而是：

1. 能早停就早停；
2. 能确定性解决就不调用模型；
3. 只有存在真实争议时才提升思考强度；
4. 模型能力由系统自动感知；
5. 文学质量与事实正确性分层处理；
6. 完全兼容 BetweenLines 现有 AI 校对体系。
