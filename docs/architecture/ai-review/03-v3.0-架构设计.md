# 一、设计目标

系统目标不是构建一个“多模型投票器”。

系统目标是构建一套：

- 高置信度早停；
- 低 Token 成本；
- 可解释；
- 可追踪；
- 可仲裁；
- 同时兼容单模型与多模型；
- 与现有 BetweenLines AI 校对体系兼容；
- 与当前 proofread-contract、term-table、low-score、web-lookup 保持一致；
- 能逐步扩展而不破坏既有数据结构；

的分层认知审核流水线。

---

# 二、核心原则

## 原则 1：确定性优先

任何能够通过确定性规则解决的问题：

- 不进入 AI；
- 不消耗 Token；
- 不进入仲裁流程；

优先级：

确定性规则 > AI 判断

---

## 原则 2：早停优先

系统必须随时尝试结束流程。

允许：

规则层结束。

允许：

Stage 1 结束。

允许：

Stage 2 结束。

只有确实存在分歧时才进入仲裁。

---

## 原则 3：能力驱动

禁止根据模型名称硬编码接口协议。

统一依赖：

model-capabilities.js

获得：

- reasoning
- reasoningEfforts
- supportsTemperature
- thinkingFormat

所有调度建立于能力画像。

---

## 原则 4：分离事实与文风

事实正确性与文学表现属于不同问题。

因此：

Stage 1
负责事实。

Stage 2
负责表达。

Stage 3
负责裁决。

不得混用。

---

# 三、统一状态机

完整流水线：

输入行
→ 对照表
→ 规则预筛
→ Stage1 Gatekeeper
→ Fast Pass
→ Stage2 Stylist
→ Low Score Attribution
→ Web Lookup
→ Arbitration Trigger Check
→ Stage3 Arbiter
→ Format Guard
→ Punctuation Normalize
→ Target Script Guard
→ Note Generation
→ Writeback Candidate

该状态机直接映射当前工作台架构。

# 四、阶段定义

## Stage 0：确定性层

组成：

- term-table
- rule prefilter
- similarity prefilter
- audit risk

职责：

发现：

- 术语问题
- 格式问题
- 显然错误
- 风险标记

结果：

1. 直接完成；
2. 跳过；
3. 进入 AI；

---

## Stage 1：Gatekeeper

定位：

事实质检员。

目标：

判断是否真的存在问题。

负责：

- 漏译
- 加译
- 错译
- 数字错误
- 否定翻转
- 主体错误
- 人名错误
- 时态错误

原则：

宁可不改。
不要润色。
不要重译。

输出：

- keep
- replace
- unclear

以及：

- needsEdit
- needsContext

---

## Fast Pass

满足：

- needsEdit=false
- 无风险标签
- 无上下文需求
- 无术语冲突

立即结束。

目标命中率：

60%-85%

具体以实测为准。

---

## Stage 2：Stylist

定位：

文学责编。

职责：

- 中文自然度
- 翻译腔消除
- 节奏优化
- 角色口吻
- 小说表现力

重要原则：

先审查初审。

再决定是否采纳。

而不是直接润色。

输出新增：

critique:
- accept
- modify
- reject
- escalate

---

## Low Score Attribution

位置：

Stage2 后。

职责：

解释极低分来源。

分类：

- shift
- context
- omission
- logic
- speaker
- uncertain

作用：

避免把所有低分问题都误判为翻译错误。

---

## Web Lookup

位置：

Low Score 后。

只在必要时启用。

典型场景：

- 专有名词
- 人名
- 组织名
- Wiki 项
- 术语争议

默认跳过。

---

## Stage 3：Arbiter

定位：

终审法官。

触发条件：

- keep vs replace 分歧
- rewrite 级改写
- 高风险标签
- attribution 无法解释
- web lookup 后仍不确定

职责：

给出唯一结论。

不负责创造新方案。

负责裁决已有方案。

# 六、单模型人格分化

目标：

解决只有一个模型可用的问题。

实现方式：

建立三个独立会话。

Session A
事实质检员。

Session B
文学编辑。

Session C
仲裁官。

共享输入。

不共享推理历史。

不共享链路状态。

避免自我确认偏见。

---

# 七、多模型编排

## 双模型

推荐：

高严格度
→ Gatekeeper

高文学性
→ Stylist

发生升级时：

以独立会话执行仲裁。

---

## 三模型

自动选择：

严格度最高
→ Gatekeeper

文学性最高
→ Stylist

推理能力最高
→ Arbiter

---

## 四模型及以上

前三者构成核心流水线。

其余模型：

作为挑战者池。

仅在特定风险触发。

# 九、备注协议

统一格式：

[AI校对]
分析：
- 发现的问题
- 分歧来源
- 仲裁理由
修改结果：最终文本

规则：

修改结果始终最后出现。

防止误写回正文。

# 十三、成功标准

系统上线后成功标准：

1. Fast Pass 命中率显著提升；
2. Token 成本低于全量多轮审核；
3. 人工确认率下降；
4. 错误写回率下降；
5. 模型切换不需要重新设计流水线；
6. 单模型模式与多模型模式得到相同架构体验。

---

# 最终结论

v3.0 不再把系统定义为多模型协作框架。

而是定义为：

一个以确定性规则为基础、以早停为核心、以认知分层为骨架、以仲裁机制为安全网的翻译校对决策系统。

多模型只是其中一种实现方式。

单模型人格分化同样是一等公民。
