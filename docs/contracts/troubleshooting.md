# 常见故障定位与排查手册

本文档按故障现象定位实现与证据；模块所有权见 [模块边界](module-boundaries.md)，输入与对齐规则见 [文本输入契约](text-input-alignment.md)，快照与写回规则见 [项目存储契约](project-storage-writeback.md)。代码更新后的重启、应用布局或重新生成操作统一按 [改动生效与交付提示](../agents/change-workflow.md#改动生效与交付提示) 执行，下文不另定义生效规则。

## 文本与对齐异常

### 1. 原文重复
- **现象**：表格中出现意外重复的原文长段落。
- **排查**：检查是否重新引入了无 reuse tracking 的 fallback，或技术 pivot interval 合并是否漏掉了重叠组。

### 2. 原文为空或段落缺失
- **现象**：表格某些行原文为空、原文段落缺失或对齐错位。
- **排查**：检查活动项目快照中的 `jp-align.json` 是否过期，或正文过滤是否改变了段落索引。原文段数大于行数时检查 `1:0` 对齐组；它的 `pivotStart === pivotEnd` 表示没有匹配译文，不得在加载时丢弃。构建器保留该组并按邻近原文位置插入空译文行，原文索引被重复使用或区间越界时拒绝构建并要求重新对齐。
- **回归**：`scripts/row-source-only.test.js` 覆盖双语、三语、空输入、重复长原文和异常区间；修复后重新生成全部输出并核验原文覆盖。

### 3. 章节标题污染正文
- **现象**：章节标题被切分成了正文段落。
- **排查**：补充 `src/ingest/text-utils.js` 中的 `chapterPatterns`，然后重新生成全部输出。

### 4. 插图附近错位
- **现象**：插图或媒体附近段落对齐错位。
- **排查**：先确认 `splitParagraphs` 是否过滤了 media-only blocks，再看 grouped moves 是否需要扩大或加局部重对齐。

### 5. Pandoc 输出混入非正文
- **现象**：导出的正文中包含元数据或非正文说明。
- **排查**：EPUB 先检查页面文件名和目录标签。`readEpubTextWithPandoc` 在临时 EPUB 中清空明确标识的非正文页，与内置 reader 共用页面语义判定；源文件不会改写。不能只过滤「制作信息」标题一行，否则该页末尾的备注仍可能被 `findBodyStart` 当作首段，连带把后续简介送入对齐。其他文档格式仍检查转换后的块级正文边界，不按整篇文本关键词扫描。
- **独立阅读提示**：无语义文件名、无目录标签的书前提示也可能被误当正文。当前仅在首个正文导航或非包装页的结构标题之前，将只有一个非空段落、以 `※本書` 开头、同时含明确阅读指令与礼貌结束语的页面标为非正文；Pandoc 与内置 reader 共用该标记。缺少明确边界、正文开始之后、有正文标题/导航、引用或正文混排（含单字段落）均保留，不按卷号、页序或字数猜测起点。
- **回归**：`scripts/epub-utils.test.js` 检查两条 EPUB 路径、原文件保留和正文内联标记；修复后重新导出、对齐、构建并核验真实首段。

### 6. 输出混入后记、特典或版权页
- **现象**：最终比较中出现了后记、附录或版权页。
- **排查**：调整 `src/ingest/text-utils.js` 的正文结束规则，然后重新运行 `npm run align:jp && npm run build`。

### 7. 对齐发生连锁错位
- **现象**：某一段错位后导致后续所有行均错位。
- **排查**：检查快照中的 `paragraphs.json` 是否混入图片占位、页码、脚注或元信息，再重新运行对齐与构建。

### 8. 两种语言从不同情节开始
- **现象**：生成成功且行数看似正常，两种语言的首段却不是同一情节。
- **排查**：比较转换后的完整文本与过滤后的段落。检查 `findBodyStart` 的简介状态是否在独立彩页/插图标题处结束；图片被移除后仍要保留随后的无标题引子，不能只用行数或首个空对齐组判成功。两侧只差整数段的开篇缺失见 #9。
- **回归**：`scripts/text-utils.test.js`；过滤修复后重新导出、对齐、构建并核验真实首段对应内容。

### 9. 开篇首段被整段丢弃，紧随一行空译文
- **现象**：表格第 1 行的原文与译文不是同一句，译文其实是下一段的内容；紧接着出现一行空译文（`1:0`，相似度为负、字数 0），此后的行才重新对上。该卷两侧段落数相差整数段，少的一侧缺的正是首段。
- **根因**：`findBodyStart` 曾以「第一个通过 `isLikelyBodyBlock` 的块」作为正文切片起点，而 `text.slice(start)` 会把起点之前的块永久丢掉。短、无引号且不以句末点号收尾的正文段落（中文开篇以逗号收尾的那种一行）会被判成非正文块，于是首段连同开篇章节标题一起被切掉，该侧比另一侧少一段，跨语言对齐随之错位一行，`1:0` 组只是对齐器在补这个缺口。
- **当前实现**：正文起点是「最近一次结构性边界（简介范围、章节标题、媒体占位）之后的第一个非前置块」；`isLikelyBodyBlock` 只用于确认已经进入正文，不再决定起点位置。开篇章节标题紧挨正文起点时仍一并保留，否则该章会降级成「正文」。副作用是开篇节号块与书内后续节号一致地进入正文。
- **排查**：比对活动快照 `paragraphs.json` 两侧段落数与各自首段；两侧都从节号开始、段数相等即说明该快照已按新规则生成。旧快照按 #2 重新对齐，仅刷新或应用新布局不修复已生成的对齐数据。
- **回归**：`node --test scripts/text-utils.test.js` 覆盖弱块引子、开篇标题保留与简介范围；修复后重新运行 `npm run align:jp && npm run build` 并核验开篇首行。

## 环境与加速器异常

### torchvision 与 torch 版本不匹配（`operator torchvision::nms does not exist`）
- **现象**：`import torchvision` 抛 `RuntimeError: operator torchvision::nms does not exist`，`import transformers` / `sentence_transformers` 随之失败；`npm run align:jp` 打印 `torchvision is installed but unusable` 后继续跑；`npm run check:accelerator` 的 `torchvision:` 一行显示 `installed but unusable`。
- **根因**：torchvision 的原生扩展按导入表绑定 torch 的 C++ 符号，版本号相同（`torch 2.12.0` ↔ `torchvision 0.27.0`）不代表 ABI 相同。ROCm/TheRock 版 torch 的 `c10/util/Exception.h` 把 `ValueError`、`NotImplementedError` 等写成 `using Error::Error;`，`c10.dll` 因此不再导出 `ValueError::ValueError(SourceLocation, std::string)` 这类派生类构造函数；PyPI 版 torchvision 的 `_C.pyd` 恰好导入它们，加载失败报 `ERROR_PROC_NOT_FOUND`，扩展缺失后到注册 Meta kernel 时才抛出上面那句。torch 装好之后被后来的 `pip install`（如 `yomitoku`、`ultralytics`）从 PyPI 补进 torchvision 就会踩中。
- **证据入口**：`.venv/Lib/site-packages/torchvision/_C.pyd` 的导入表减去 `.venv/Lib/site-packages/torch/lib/{c10,torch_cpu}.dll` 的导出表（`llvm-readobj --coff-imports` / `--coff-exports`；ROCm 环境可直接用 `_rocm_sdk_core/lib/llvm/bin/llvm-readobj.exe`）。
- **处置**：torch / torchvision / torchaudio 必须来自同一次安装、同一来源；换 torch 后端时连 torchvision 一起换。ROCm 侧对应 TheRock 多架构索引 `https://rocm.nightlies.amd.com/whl-multi-arch/`，torchvision 版本需与 torch 对应，GPU 算子还要 `amd-torchvision-device-<gfx>` 内核包（只装基础轮子时 CPU 算子正常、GPU 算子报 `hipErrorInvalidImage`）。设备内核包的 METADATA 把 `rocm-sdk-device-<gfx>` 锁到同日 nightly，与本机发布版并存时 `pip check` 会报一条版本不一致，属预期，按同一条 ROCm 线工作即可。对齐流程本身不需要 torchvision，`align_jp.py` 会把它标记为缺失后继续；确认不再需要时可 `pip uninstall torchvision`。
- **回归**：`npm run check:accelerator` 应打印 `torchvision: <版本>`；出现 `installed but unusable` 即复发。

## 模式裁剪与第三列泄露

### 双语产物出现第三列内容
- **现象**：双语模式下出现 `TW paragraphs: 0`、`counts.tw`、行里的 `tw`/`twCn`/`refinedScore`、页面上的“台版/参考文本”。
- **排查**：
  1. 先确认活动快照是否由旧版本生成——模式裁剪只对新构建生效，重新运行 `npm run align:jp && npm run build`。
  2. 若重新生成后仍存在，检查是哪一层又把 `tw` 加了回来：
     - `validateSelection`
     - `loadParagraphs`
     - `rowFieldsFor`/`exportRows`
     - `makeHtml` 的 `pageLabels`。

## 备注导入与保存异常

### 清空当前项目后仍无法导入备份
- **历史根因**：历史列表按项目隔离，同源 `localStorage` 却由全部项目和配置共用；清空当前项目仍可能不足以容纳备份与当前空间。
- **当前实现**：控制台页面的完整备注由 `notes-file-store.js` 长期落盘，`notes-disk-storage.js` 迁移全部旧浏览器空间并在回读核验后释放副本。新保存不受浏览器配额限制；直接打开 HTML 仍走旧浏览器模式。空间与快照清理独立，详见 [备注契约](workbench-notes-spaces.md#长期磁盘存储与旧空间迁移)。
- **恢复**：先保留未保存页面与 JSON。重启控制台服务，应用新布局，再从控制台打开工作台迁移；页面未显示「已保存到电脑」前保留原页。迁移同名冲突保留副本；磁盘写入失败检查服务与目录权限，版本冲突先导出再重新加载，不能删除别的项目来掩盖磁盘失败。已删除的浏览器记录需从现存备份恢复。
- **回归**：`node --test scripts/notes-disk.test.js scripts/notes-routes.test.js scripts/notes-storage.test.js scripts/notes-recovery-seed.test.js`，覆盖磁盘恢复、迁移失败保护、项目保留、损坏数据、接口鉴权和跨页冲突。

## AI 阶段进度异常

### 模型为空仍能开始，随后逐行累积异常
- **根因**：开始按钮只按运行状态禁用，没有检查实际模型；适用列表会过滤空模型，服务端清洗又会丢弃空模型子配置或用协议默认值覆盖显式空值，导致无效配置进入派发或意外回退。
- **当前实现**：页面在按钮状态、启动及重跑清空前共用模型就绪检查；服务端在队列与运行状态变更前校验参与阶段的每个连接，热更新也先校验后应用。显式空模型保留用于报错，预设不再因模型为空而被静默丢弃；独立阶段只校验自身，一键开始校验全部参与阶段。
- **回归**：`node --test scripts/ai-start-validation-client.test.js scripts/ai-stage-controls.test.js scripts/ai-stage-controls-client.test.js`。服务端修复需重启控制台服务，页面修复需应用新布局后 F5。

### 校对运行时悬停说明反复闪烁

- **根因**：状态轮询持续改写原生 `title`，适用预设列表又每次重建全部节点，导致浏览器重新触发提示或丢失悬停锚点。
- **当前实现**：动态提示按 [实时悬停契约](workbench-notes-spaces.md#浮动提示toast与进度承载分工) 保留当前停留的快照，数字与 ARIA 继续更新；预设条目按 ID 复用。停止、隐藏与清除仍立即撤销过期运行信息。
- **回归**：`node --test scripts/ai-live-hover-client.test.js`，运行生成页面的真实脚本，检查连续状态响应期间 `title` 零写入、节点身份稳定、离开后更新及失效清理。页面改动需「应用新布局」后 F5。

### 卡片很宽，但进度轨道与待办只挤在左侧

- **根因**：卡片正文由 Flex 改为 Grid 后，继承了共享样式的 `justify-content: flex-start`，且未声明列宽；隐式 `auto` 列按内容收缩。仅验证等高和进度条纵坐标会漏掉这一问题。
- **当前实现**：正文声明显式单列并拉伸，运行区与主指标铺满卡片内容区，待办贴合右侧。固定轨道与完整几何验证要求见 [工作台契约](workbench-notes-spaces.md#浮动提示toast与进度承载分工)。
- **回归**：`node --test scripts/ai-stage-metrics.test.js` 验证结构与待办筛选；另用真实 DOM 按契约检查左右边界、文字范围和启停稳定性，覆盖各阶段计数不同的超宽场景。假 DOM 的零尺寸不能代替布局验收。

### 阶段二已有适用预设，阶段三候选下拉仍无法切换
- **根因**：依赖更新只修改原生选择器的 `disabled`，没有同步增强下拉的可见按钮；添加按钮已经解锁，可见候选按钮却保留禁用状态。恢复配置时的中间禁用状态也可能残留。
- **当前实现**：`updateStagePresetDependencies` 更新阶段三原生控件后调用 `syncEnhancedSelect`，同步可见按钮的禁用状态与候选文案。
- **回归**：`node --test scripts/stage-preset-binding.test.js`，运行真实增强下拉脚本，覆盖阶段二添加、移除、重加与恢复，以及可见菜单打开、候选切换和仅选择不启用。

### 适用预设显示「未启用」，启动后却继续复审或仲裁
- **根因**：适用摘要读取已添加列表，旧执行与保存逻辑却在列表为空时回退读取候选选择器，尚未添加或移除最后一项后残留的候选被隐式启用。
- **当前实现**：显示与配置统一读取已添加列表；候选选择不进入启动请求和持久化，旧单预设存档只在恢复入口迁入列表。运行中移除全部预设仍按既有热更新契约回落阶段配置；如需改变本次流水线覆盖范围，应停止后重新启动。
- **回归**：`node --test scripts/stage-preset-binding.test.js`，覆盖三个阶段的候选未添加、启动请求、移除最后一项、刷新恢复与旧存档兼容。

### 未启用复审，修改结果仍出现可点击的复审版本
- **根因**：版本按钮按改案字段的宽松兜底显示，通用修改结果被当作复审稿，没有同时核对阶段是否执行、本行是否待审及已添加预设；点击入口也没有共用同一版本状态。
- **当前实现**：显示、禁用和切换统一读取阶段版本状态，待执行只复用最新轮次判据；配置变化仅刷新可见版本栏。已有真实改案、局部提议及无默认成品的边界见 [工作台契约](workbench-notes-spaces.md#修改结果的阶段版本)。更新页面按刷新契约应用新布局并刷新。
- **回归**：`node --test scripts/stage-revision-buttons.test.js scripts/stage-review-reports.test.js`。

### 流水线已收尾但仍显示待复审、修改结果空白
- **根因**：旧备注解析按空行切块，多段初审改案里的首个空行截掉后面的复审、仲裁与修改结果字段。服务端日志可以已经记录复审完成和仲裁定案，页面却仍将该行计入待复审，并把空修改结果保存下来。
- **当前实现**：共享轮次解析按标记和字段边界保留完整记录，客户端与服务端按完整多行字段读取及清空。末尾改案续段须与独立阶段改案匹配，避免把人工尾注并入可写回正文；旧截断遗留的空改案按 AI 契约恢复，保留人工编辑。
- **回归**：`node --test scripts/stage-note-state.test.js scripts/multiline-stage-notes.test.js`，覆盖 LF/CRLF、待办与完成计数、完整段落、增量回包、重跑清空、人工尾注与旧记录恢复。

### 点击开始后初审进度倒退
- **根因**：旧页面的初审分母在静止时只包含已有结论和异常，漏掉尚未审过的行；运行时又把本轮队列加进来，而且异常重试行已经在队列中，导致重复计数。已有通过、提改与存疑记录不一定减少，不能只凭进度条长度判定数据回滚。
- **当前实现**：`renderStageMetricsDashboard` 始终使用当前工作台全行范围表示初审覆盖。聚合兼容输入以已完成加队列、异常两者最大值作下界；停止时同时显示未审与异常。复审和仲裁的实际候选范围仍可随上游产出增长，不锁定历史最高百分比。
- **回归**：`node --test scripts/ai-progress-resume.test.js scripts/ai-stage-metrics-regression.test.js scripts/ai-stage-metrics.test.js`，覆盖真实点击续跑、队列含异常、停止、刷新、成功增量、空文本行与已有备注和签名保留。

### 阶段三正在仲裁，阶段二仍显示同一行待复审或异常
- **根因**：复审成功只更新实时计数并移交仲裁，新行备注等仲裁收尾才发布；页面仍按旧失败备注统计待复审与异常。同一运行重试还曾只清理异常明细，遗漏服务端累计的下游异常数。
- **当前实现**：复审交接时发布「已复审、待终审」中间结果，立即替换旧失败备注；仲裁成功或失败通过同一修订游标覆盖，处理数量只在整行收尾时累计。重试同步撤销旧下游异常数，仲裁中的行只留在仲裁待办；显式待终审的复审记录可直接恢复仲裁。
- **回归**：`node --test scripts/ai-stage-controls.test.js scripts/stage-note-state.test.js scripts/ai-stage-metrics-regression.test.js`，覆盖真实请求交接、成功/失败仲裁、同一运行重试、页面异常归属与复审采纳但无改案的待终审恢复。

## 写回异常

### 1. 写回定位失败或写错位置
- **现象**：点击写回后提示定位失败或修改了错误的段落。
- **排查**：
  1. 先确认目标类型是否被正确识别（四种 `TARGET_*` 之一）。
  2. 检查原文件块的文本是否与行文本一致；含内联标记的段落必须走块级匹配路径，不能回退到朴素字符串替换。定位失败的行不得写入。
  3. 文本肉眼一致却仍然失败时，先核对不可见字符口径（提取端会丢弃而写回端保留的字符会造成永久失败），见下文「段落带零宽空格的行永远报未能在原文件中定位段落」。

### 2. 写回落到了同一段文字的另一处（重复段落错位）
- **现象**：同一卷里两处相同的 `<p>`，写回第 2 处时却改到了第 1 处。
- **排查**：
  1. 页面脚本由 `render-workbench.js` 在渲染时读取并内嵌，老快照仍可能发不带 `rowTexts` 的请求——点「应用新布局」（或 `npm run layout`）并 F5 后再写回。
  2. 新页面仍错位则看服务端收到的请求体里有没有 `rowTexts[targetKey]`（第 i 行对应下标 i-1，最后一个条目之后额外带最多 32 行定位上下文）、行号是否与页面行号一致，以及上下文是否仍与原文件相符。后方上下文只界定位置，不生成额外写回条目。
  3. 前文已经修改时，核对 `buildRowBounds` 给出的前后唯一段落范围。边界仅来自页面与原文件都唯一的完整段落，不能按行号或块数推算落点。被顺序一致的前后边界排除的旧文本不再作锚点；无法消解的边界倒序拒绝落位。单段未落地的同文只阻止其候选范围内的后续行；部分匹配的多段行仍保持保守拦截。

### 3. 写回后成品里混进说明字段
- **现象**：写回后成品里混进「低分归因：」「线上查证：」这类备注说明。
- **排查**：
  - 说明行原本跟在「修改结果：」后面，被客户端的按行解析并进了修改结果（`public/workbench-client.js` 的 `parseAutomatedNote`），而修改结果正是人工点「写回」送出的文本。
  - 新备注把这两类说明写进分析栏（`decisionToResult` 的 `analysisLines`，排在「修改结果：」之前），旧备注在页面载入时由 `normalizeStoredNote` 按行剥掉；仍复现就先确认常驻 AI 实现与内嵌页面都已按刷新契约更新，再看备注里的「修改结果：」是不是最后一段。

### 4. 位置唯一的一行也报「有多处同段」，同文本的行整卷连坐
- **现象**：某行的段落文本在原文件里位置唯一、行序锚点也已经停在它上面，写回却报 `原文件中有多处同样的段落…` 或 `本行前面有同一段文字的行没能写回（…）`；同一卷里所有同文本的行一起不落地（真实事件：`某卷` 第七章 `<p>也就是说。</p>`）。
- **根因**：源文件里连续 N 段同样的短句（真实事件：第二章连续三段 `<p>也就是说。</p>`）触发「近处重复即歧义」，那一行没占住它的文本；旧的 `unresolved` 按文本全卷记忆，后面同文本的行被连坐。
- **当前实现**：`locate` 在「剩下的同文本行数 === 从候选起严格连续的同文本块数」时按行序落位，数量对不上仍报歧义；`unresolved` 记下未落地那一簇的最后一块，后面的行只有首个候选仍落在簇内才拦（`src/ingest/writeback.js`）。仍复现就先确认常驻服务已重启（写回定位属常驻进程代码），再看请求体里 `rowTexts[targetKey]` 是否覆盖到该行。

### 4a. 原句还在，旧快照写回却报「未能定位」
- **现象**：前文已经批量修改，剩余几处重复短句仍保持原文，却无法单行写回。
- **根因**：旧行序清单逐行向后扫描，前文旧短句可能命中另一章的同文，游标越过真正目标；同时只发送到待写行，缺少后文边界，隔一段出现的重复句会一起判歧义。
- **当前实现**：共享定位器预先建立唯一上下文范围，`locate` 的下界与上界同时应用于未修改行、文本替换和说话人标注；范围内仍有多个候选时拒写。两个客户端额外携带后方上下文，解决重复句缺少右边界的问题，不改页面行数据或备注空间键。
- **验证**：`node --test scripts/writeback.test.js scripts/writeback-export.test.js scripts/confirm-dialog.test.js`。真实样本仅做内存定位计划，核对落点与 `missed` / `ambiguous`，不得为验证直接写入源文件。

### 5. 成品里出现被终审否决的阶段改案
- **现象**：AI 明确「维持原译 / 复审驳回」的行，成品段落却被换成初审或复审的过程稿，句子读起来别扭（真实事件：某卷 14 行，如「金钱方面的事情」「慌乱」「那是在不久之后。」）。
- **根因**：客户端 `parseAutomatedNote` 曾把上游改案无条件回填成下游阶段的定案，`revisionTextFor` 再按「仲裁 ＞ 复审 ＞ 初审」把它当成默认修改结果；批量写回遂把否掉的方案写进源文件。
- **当前实现**：下游阶段明确「驳回 / 维持原译 / 存疑」时不再回填；`是否需要修改：否` 的行不生成默认修改结果；存量备注在载入时清掉「正好等于某个阶段改案」的自动推导值，人工写过的文本与显式切换过版本的记录保留（`public/workbench-client.js`）。页面脚本内嵌在快照里——要先「应用新布局」+ F5，存量备注才会按新规则归一化。

### 6. 段落带零宽空格的行永远报「未能在原文件中定位段落」
- **现象**：某些行反复写回失败，提示 `未能在原文件中定位段落：…`，但把这段文字和原文件对照看起来一模一样（真实事件：`某卷` 第二章 3 行，段落尾部各带 4 个 `U+200B`，批量写回后只有这几行没落地）。
- **根因**：提取端 `html-to-text`（`epubHtmlToText`，见 `src/ingest/epub-utils.js`）把零宽空格当可折叠空白——段中折成空格、段尾直接丢掉——工作台行文本因此不含它；而写回端 `comparableText` 只去 `\s`，JS 的 `\s` **不**匹配 `U+200B`，块的可比文本多出这些字符，严格相等判定随之失败。定位失败是「行文本与块文本对不上」的忠实上报，不是锚点或歧义问题。
- **当前实现**：写回端与提取端同口径忽略 `U+200B`，替换区间收缩到可见文本，原文件里的这些字符留在原位（`src/ingest/writeback.js` 的 `comparableText` 与 `documentBlocks`）。仍复现就先确认常驻服务已重启（写回定位属常驻进程代码），再按十六进制核对这一段的原始字节里是否有别的不可见字符。

## 格式门禁、标点与语言异常

### 1. 修改结果里出现换行或空行
- **现象**：页面上「修改结果」文本框变成两行、写回后成品段落被拆开。
- **排查**：
  - 这是成品格式门禁（`ai/format-guard.js`）拦截的形状。历史故障中，旧对齐快照把多段原文与单段目标文本放在一行，页面把换行渲染成空格后不易察觉；模型据此误判「译文把原文换行丢了」并往 `revisedText` 插入 `\n`，写回按 `\n{2,}` 切分时随之错段。当前构建必须遵守单原文段落不变量；先核对该行是否来自旧快照，再查门禁输出。
  - 门禁会并回模型插入的换行/空行/`<br>` 并在备注分析栏写一行「格式自动规范化：…」，段结构与 noteref 标记对不上的修订直接作废；终审前转终审，终审改案仍不合格时保留原译并记录原因，详见 [AI 契约](ai-proofread-contract.md#终审二元定案)。
  - 若仍能写回出换行：确认常驻 AI 实现已更新，再检查这一层是否被 `formatGuard:false` / `TRANSCOMPARATOR_FORMAT=0` 误关闭。

### 2. 修订结果里的标点被改坏
- **现象**：英文句子被全角化、`3.5`/`e.g.`/URL 里的点被换成 `。`。
- **排查**：
  - 检查 `ai/punctuation.js` 的语境判据：半角→全角只在标点两侧出现中日文时生效；全角→半角要求正向 ASCII 证据（两侧都是字母/数字，或一侧是、另一侧是行边界且整段无汉字/假名），纯标点行与中文句子不会被误还原；紧贴 ASCII 字母/数字的点有豁免；内联标记整段先摘后还原。
  - 修改结果仍出现 `“…”` 时看 `status.punctQuoteVoids` 与备注；无法配对或英文语境弯引号作废该修订，终审前转终审，终审后保留原译，具体语境与规范化规则见 [AI 契约](ai-proofread-contract.md#2-输出侧标点规范化aipunctuationjsnormalizedecisionpunctuation)。
  - 若某一行的标点确实不该动，确认是否被标签外语境带偏，或通过 `punctNormalize:false` / `TRANSCOMPARATOR_PUNCT=0` 临时关闭。

### 3. 修订结果里唐突出现日文
- **现象**：`revisedText`、备注的「修改结果：」或写回后的成品里混进假名/日文标记。
- **排查**：
  - 先看那一行的原文是否带注音标记（`<ruby>基文<rt>注文</rt></ruby>`）而目标列没有——这是最常见诱因，模型判定“译文漏了注音”却没有目标列读音可写，只能照抄日文。
  - 注意 A 列取自 `index-X/.cache/epub-work/japanese-text/`，那是 `bw_preprocess.py` 的预处理产物：普通读音已被合并丢弃，「A 里看不到注音」不等于原版没有注音。判断注音要回上游的 BookWalker 分页源；`profiles/novel.js` 的 `ruby` 条目已按缺失证据处理——既不得凭空补注音，也不得据此要求删掉成品已有的注音。
  - 查看 `status.scriptLeaks` 与任务结束的「输出语言护栏」日志。
  - 若计数为 0 却仍有日文：检查 `ai/row-features.js` 的 `ruby` 规则是否覆盖了原文侧 HTML 形态，以及用户自定义提示词是否残留旧版通用侧整段；先按刷新契约更新常驻 AI 实现与页面，再点「恢复默认」。

### 4. 成对标记内侧的句末点号被误删
- **现象**：AI 判「对话尾部引号前多出句号」，并在 `revisedText` 里删掉句末点号。
- **排查**：
  - 目标列（中文）完整引述或括注时，句末点号在标记内；日文常省略该点号。
  - 该口径已写入 `profiles/novel.js` 按行条目并由 `quote`/`parenthesis` 触发；输出侧 `restoreTerminalPunctuation` 会自动补回被删的点号（`status.punctRestored`）。
  - 若模型依然报错或给错 summary，检查是否命中对应特征，并确认点号是否在完整句内。

## 预筛选异常

### 人名被标点断开后未命中译名表，模型反而改坏标准译名

- **现象**：表中已有完整人名，正文却写成「青山、春人」或「青山……春人」，页面不显示该条术语，模型按自身知识把项目采用的译名回改成表外写法。
- **根因**：连续子串匹配只识别完整写法；断开的姓名退成姓或名的分段命中，随后被防同姓误匹配规则排除，标准译名没有进入模型提示词。译文侧若只凭正确姓氏确认一致，也可能掩盖完整姓名中名字的错误。
- **当前实现**：人名完整基文别名按受限行内分隔符匹配；匹配、覆盖率、页面术语块和模型提示词使用同一口径。完整标准译名也按该口径比对，保留正文标点。只姓或名、非人名及跨句拼接继续按各自边界处理，详见 [译名表契约](ai-proofread-contract.md#判定口径与注音规则)。
- **排查与恢复**：确认项目挂载的表中有该词条且类型为人名；重启控制台服务加载新规则，已有页面点「应用新布局」后刷新以重算术语标签。旧已完成审核结果不会自动改回，需核对原文、标准译名及已有改案，再对受影响行重新校对；人工确认仍按原有跳过规则保留。

### 引号或标点不同却被标成 100% 相似并跳过

- **根因**：正文相似度会删除标点与符号，若守卫只保护英文和数字词元，`『……』` 与 `「……」` 等差异就会被抹平；行内已有的高相似度分数也可能放行。
- **当前实现**：独立预筛与 AI 初审共用标点守卫，归一化后标点、符号的字符或位置有差异就留给模型。规则与定向验证见 [AI 契约](ai-proofread-contract.md#确定性预筛与相似度守卫)。
- **排查**：先按刷新契约更新常驻服务；历史预筛结论不会随服务重启自动重算，重查旧行需先清除该行旧自动结论再重新预筛或校对。已人工确认的行仍按人工确认跳过。

## 模型输入缓存命中偏低或显示「—」

- 先查看缓存徽标的悬停明细：「—」可能是没有输入分母、接口未报告或返回数据不一致，不能直接判为零命中。混用接口时只统计明确报告的调用，完整字段口径见 [缓存统计契约](ai-proofread-contract.md#token-用量与缓存命中统计)。
- 区分启动阶段与稳定运行阶段，再核对同一模型、模式、档案的稳定 system 前缀是否一致；自定义提示词、规则或全局术语表变化都会改变前缀。按行命中的资料应位于稳定边界之后，不能把整份规则强行全量注入来追求百分比。
- Claude 原生请求应在固定 system 块带缓存断点，动态块和当前行不带；compatible 请求不应携带内部标记。服务是否建立缓存、模型最小长度与网关支持按供应商规则判断，降低并发不能修复前缀分叉。实现与离线验证见 [提示词组装契约](ai-proofread-contract.md#提示词五层组装体系)。

## 特化规范与服务启动异常

### 1. 特化规范“没生效”或提示词突然变短
- **排查**：
  - 查看 `promptLayerReport()` 的 `profileLines` 与 `entities`。
  - 确认条目是否被误写成按行条目（应当常驻的语义规则却声明了 `features` 或 `characters`）。
  - 确认 `features` 的 id 是否在 `ai/row-features.js` 中注册。
  - 确认 `characters` 中的名字是否与文本中的写法一致（名字写错或别名写窄会导致整卷一次都不注入）。
  - 先按刷新契约更新常驻 AI 实现与页面，再点「恢复默认」。
  - 上游 `index-X/docs/translation-spec.md` 改动后未同步 AI 档案时，表现为「模型按旧口径判缺陷」（把规范允许的写法判成问题，或反过来放过真缺陷）。对照该文件 §七 的「AI 档案」列确认这一条有没有落到条目里：招呼语与否定拟声不音译、不得凭空创建注音与 A 列预处理的证据边界、间隔号与西文缩写、赛事项目名的「公里」例外、行末点号不逐行比对日文、外国人名按原语还原。

### 2. 双击 `start-setup.bat` 提示「127.0.0.1 拒绝连接」
- **现象**：浏览器打开后短暂显示无法连接。
- **排查**：
  - 控制台页面必须由服务端在 `server.listen` 回调里打开（由 `start-setup.bat` 设 `TRANSCOMPARATOR_OPEN_BROWSER=1` 驱动）。
  - 启动脚本不得使用固定 `timeout` 猜测启动耗时；端口应使用 `server.address().port` 动态获取。若端口被占用，服务端会报 `EADDRINUSE` 退出。

## 页面交互卡顿（鼠标变慢 / 输入延迟 / 开关卡顿）

### 1. 开关审核轨迹、抽屉、拖窗口之后鼠标移动变慢、输入有延迟
- **根因**：主线程被强制同步布局占满，不是渲染（paint）卡顿。凡是「写样式后立即读几何属性」的地方，浏览器都必须先把待处理的样式与布局算完；在 500 行的表格上，一次就是一次整表重排。
- **排查顺序**：
  1. `updateResultsMaxHeight` 为数可见行而查表格 DOM，导致重渲染后同步布局。
  2. `measureRevisionEditors` 整批量高时逐行交错读写；历史 500 个输入框场景从 296ms 降到 15.8ms，证据说明成本来自重复布局。
  3. 事件处理器逐行量高、`resize` 重复做全量同步，或同一轮重复查询输入框列表。
- **实现边界**：缓存失效条件、批量读写顺序与行数来源统一见 [工作台契约](workbench-notes-spaces.md#客户端布局缓存边界)。
- **验证证据**：`scripts/workbench-layout-sync.test.js` 用计数假 DOM 断言布局调用边界。历史 CDP 观测的 500 行场景修复后只剩重建 DOM 的一次 Layout（约 173ms）；这是该场景的记录，不是所有页面的固定性能预算。修改后按仓库要求运行测试，不做浏览器截图验证。

### 2. 审核轨迹的展开/收起在筛选、翻页、改每页行数后回弹
- **现象**：用户手动收起某一行的审核轨迹，一旦触发重渲染（筛选、翻页、改每页行数、AI 结果到达），它又弹回默认展开态，只能反复点。
- **根因**：重渲染会重建全部行节点，`renderNoteSummary` 每次按 `isNeedsCheck` 重新算默认值，DOM 上的 `hidden` 被整体冲掉。展开状态不是备注数据，不能落盘，但在会话内必须记住。
- **实现边界**：会话状态 `pipelineOpenOverrides` 的读写与默认值由 [工作台契约](workbench-notes-spaces.md#客户端布局缓存边界) 规定；检查重渲染是否仍使用该状态。
- **注意**：这类回弹不只是体验问题——用户每重开一次就要再点一次，而每次点击都可能连带一次重渲染，这正是「越点越卡」的放大器。
