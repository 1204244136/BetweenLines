# 常见故障定位与排查手册

本文档是 `AGENTS.md` 中关于数据对齐、正文过滤、写回、格式门禁与服务启动等常见故障的排查手册。

---

## 文本与对齐异常

### 1. 原文重复
- **现象**：表格中出现意外重复的原文长段落。
- **排查**：检查是否重新引入了无 reuse tracking 的 fallback，或技术 pivot interval 合并是否漏掉了重叠组。

### 2. 原文为空
- **现象**：表格某些行原文为空或对齐错位。
- **排查**：检查活动项目快照中的 `jp-align.json` 是否过期，或正文过滤是否改变了段落索引。

### 3. 章节标题污染正文
- **现象**：章节标题被切分成了正文段落。
- **排查**：补充 `src/ingest/text-utils.js` 中的 `chapterPatterns`，然后重新生成全部输出。

### 4. 插图附近错位
- **现象**：插图或媒体附近段落对齐错位。
- **排查**：先确认 `splitParagraphs` 是否过滤了 media-only blocks，再看 grouped moves 是否需要扩大或加局部重对齐。

### 5. Pandoc 输出混入非正文
- **现象**：导出的正文中包含元数据或非正文说明。
- **排查**：优先调整转换后的块级正文边界规则，不要回退到按整篇文本关键词扫描。

### 6. 输出混入后记、特典或版权页
- **现象**：最终比较中出现了后记、附录或版权页。
- **排查**：调整 `src/ingest/text-utils.js` 的正文结束规则，然后重新运行 `npm run align:jp && npm run build`。

### 7. 对齐发生连锁错位
- **现象**：某一段错位后导致后续所有行均错位。
- **排查**：检查快照中的 `paragraphs.json` 是否混入图片占位、页码、脚注或元信息，再重新运行对齐与构建。

## 模式裁剪与第三列泄露

### 双语产物出现第三列内容
- **现象**：双语模式下出现 `TW paragraphs: 0`、`counts.tw`、行里的 `tw`/`twCn`/`refinedScore`、页面上的“台版/参考文本”。
- **排查**：
  1. 先确认活动快照是否由旧版本生成——模式裁剪只对新构建生效，重新运行 `npm run align:jp && npm run build`。
  2. 若重新生成后仍存在，检查是哪一层又把 `tw` 加了回来：
     - `validateSelection`
     - `loadParagraphs`
     - `rowFieldsFor`/`exportRows`
     - `makeHtml` 的 `pageLabels`。

## 写回异常

### 1. 写回定位失败或写错位置
- **现象**：点击写回后提示定位失败或修改了错误的段落。
- **排查**：
  1. 先确认目标类型是否被正确识别（四种 `TARGET_*` 之一）。
  2. 检查原文件块的文本是否与行文本一致；含内联标记的段落必须走块级匹配路径，不能回退到朴素字符串替换。定位失败的行不得写入。

### 2. 写回落到了同一段文字的另一处（重复段落错位）
- **现象**：同一卷里两处相同的 `<p>`，写回第 2 处时却改到了第 1 处。
- **排查**：
  1. 页面脚本是构建期内嵌的（`build-compare.js` 在 require 时 `readFileSync` 读 `public/workbench-client.js`），老页面仍发不带 `rowTexts` 的请求——先重新生成工作台再写回。
  2. 新页面仍错位则看服务端收到的请求体里有没有 `rowTexts[targetKey]`（第 i 行对应下标 i-1，只发到最靠后的那个条目为止）、行号是否与页面行号一致，以及前面那些行是否真的能在原文件里定位到（前面某一行定位失败会让它没占住的那段文字被记进 `unresolved`，后面的同名段落随之判 `ambiguous` 而不是写到前一处）。

### 3. 写回后成品里混进说明字段
- **现象**：写回后成品里混进「低分归因：」「线上查证：」这类备注说明。
- **排查**：
  - 说明行原本跟在「修改结果：」后面，被客户端的按行解析并进了修改结果（`public/workbench-client.js` 的 `parseAutomatedNote`），而修改结果正是人工点「写回」送出的文本。
  - 新备注已把这两类说明写进分析栏（`decisionToResult` 的 `analysisLines`，排在「修改结果：」之前），旧备注在页面载入时由 `normalizeStoredNote` 按行剥掉；仍复现就先确认页面是重新 `npm run build` 之后打开的，再看备注里的「修改结果：」是不是最后一段。

## 格式门禁、标点与语言异常

### 1. 修改结果里出现换行或空行
- **现象**：页面上「修改结果」文本框变成两行、写回后成品段落被拆开。
- **排查**：
  - 这是成品格式门禁（`ai/format-guard.js`）拦截的形状。先看那一行的目标列是不是单段、而原文列是多段——原文列多段、目标列单段时（页面把换行渲染成空格，人眼看不出来），模型会据此判「译文把原文换行丢了」并往 `revisedText` 里插 `\n`；而写回是按 `\n{2,}` 分段、替换段与原文段按顺序一一对应，于是替换文本被切错段。
  - 门禁会并回模型插入的换行/空行/`<br>` 并在备注分析栏写一行「格式自动规范化：…」，段结构与 noteref 标记对不上的行直接作废转人工。
  - 若仍能写回出换行：确认页面是否已重新 `npm run build`，再检查这一层是否被 `formatGuard:false` / `TRANSCOMPARATOR_FORMAT=0` 误关闭。

### 2. 修订结果里的标点被改坏
- **现象**：英文句子被全角化、`3.5`/`e.g.`/URL 里的点被换成 `。`。
- **排查**：
  - 检查 `ai/punctuation.js` 的语境判据：半角→全角只在标点两侧出现中日文时生效；全角→半角要求正向 ASCII 证据（两侧都是字母/数字，或一侧是、另一侧是行边界且整段无汉字/假名），纯标点行与中文句子不会被误还原；紧贴 ASCII 字母/数字的点有豁免；内联标记整段先摘后还原。
  - 修改结果仍出现 `“…”` 时看 `status.punctQuoteVoids` 与备注：成对中文语境弯引号转 `「…」`；无法配对或英文语境弯引号作废转人工。
  - 若某一行的标点确实不该动，确认是否被标签外语境带偏，或通过 `punctNormalize:false` / `TRANSCOMPARATOR_PUNCT=0` 临时关闭。

### 3. 修订结果里唐突出现日文
- **现象**：`revisedText`、备注的「修改结果：」或写回后的成品里混进假名/日文标记。
- **排查**：
  - 先看那一行的原文是否带注音标记（`<ruby>基文<rt>注文</rt></ruby>`）而目标列没有——这是最常见诱因，模型判定“译文漏了注音”却没有目标列读音可写，只能照抄日文。
  - 注意 A 列取自 `index-X/.cache/epub-work/japanese-text/`，那是 `bw_preprocess.py` 的预处理产物：普通读音已被合并丢弃，「A 里看不到注音」不等于原版没有注音。判断注音要回上游的 BookWalker 分页源；`profiles/novel.js` 的 `ruby` 条目已按缺失证据处理——既不得凭空补注音，也不得据此要求删掉成品已有的注音。
  - 查看 `status.scriptLeaks` 与任务结束的「输出语言护栏」日志。
  - 若计数为 0 却仍有日文：检查 `ai/row-features.js` 的 `ruby` 规则是否覆盖了原文侧 HTML 形态，以及用户自定义提示词里是否残留旧版通用侧整段（需点「恢复默认」，且必须先重新 `npm run build`）。

### 4. 成对标记内侧的句末点号被误删
- **现象**：AI 判「对话尾部引号前多出句号」，并在 `revisedText` 里删掉句末点号。
- **排查**：
  - 目标列（中文）完整引述或括注时，句末点号在标记内；日文常省略该点号。
  - 该口径已写入 `profiles/novel.js` 按行条目并由 `quote`/`parenthesis` 触发；输出侧 `restoreTerminalPunctuation` 会自动补回被删的点号（`status.punctRestored`）。
  - 若模型依然报错或给错 summary，检查是否命中对应特征，并确认点号是否在完整句内。

## 特化规范与服务启动异常

### 1. 特化规范“没生效”或提示词突然变短
- **排查**：
  - 查看 `promptLayerReport()` 的 `profileLines` 与 `entities`。
  - 确认条目是否被误写成按行条目（应当常驻的语义规则却声明了 `features` 或 `characters`）。
  - 确认 `features` 的 id 是否在 `ai/row-features.js` 中注册。
  - 确认 `characters` 中的名字是否与文本中的写法一致（名字写错或别名写窄会导致整卷一次都不注入）。
  - 页面上需点「恢复默认」，并确保页面是重新 `npm run build` 后打开的。
  - 上游 `index-X/docs/translation-spec.md` 改动后未同步 AI 档案时，表现为「模型按旧口径判缺陷」（把规范允许的写法判成问题，或反过来放过真缺陷）。对照该文件 §七 的「AI 档案」列确认这一条有没有落到条目里：招呼语与否定拟声不音译、不得凭空创建注音与 A 列预处理的证据边界、间隔号与西文缩写、赛事项目名的「公里」例外、行末点号不逐行比对日文、外国人名按原语还原。

### 2. 双击 `start-setup.bat` 提示「127.0.0.1 拒绝连接」
- **现象**：浏览器打开后短暂显示无法连接。
- **排查**：
  - 控制台页面必须由服务端在 `server.listen` 回调里打开（由 `start-setup.bat` 设 `TRANSCOMPARATOR_OPEN_BROWSER=1` 驱动）。
  - 启动脚本不得使用固定 `timeout` 猜测启动耗时；端口应使用 `server.address().port` 动态获取。若端口被占用，服务端会报 `EADDRINUSE` 退出。

## 页面交互卡顿（鼠标变慢 / 输入延迟 / 开关卡顿）

### 1. 开关审核轨迹、抽屉、拖窗口之后鼠标移动变慢、输入有延迟
- **根因**：主线程被强制同步布局占满，不是渲染（paint）卡顿。凡是「写样式后立即读几何属性」的地方，浏览器都必须先把待处理的样式与布局算完；在 500 行的表格上，一次就是一次整表重排。
- **排查顺序**（按实测代价从大到小）：
  1. **为取可见行数而查 DOM**：`updateResultsMaxHeight` 里若有 `tbody.querySelectorAll("tr[data-index]").length`，重渲染后就是一次整表强制布局（实测 500 行 **233ms**）。行数必须由 `renderVisibleRows` 传入切片长度，或取自 `renderedRowsById.size`。
  2. **整批量高的读写没分离**：逐行「写 `height:auto` → 读 `scrollHeight` → 写回」交错，每行一次整表重排（实测 500 个输入框 **296ms**）。必须走 `measureRevisionEditors` 的三段式（整批写 → 连续读 → 统一写回），实测 **15.8ms**。
  3. **事件处理器逐行量高**：新增处理器时写了 `for (const editor of ...) syncRevisionEditorHeight(editor)`，或 `resize` 每个事件都做一次全量同步（应合并到一帧，并在尺寸稳定后才重量一次）。
  4. **整段同步里重复查 DOM**：`querySelectorAll(".revision-editor")` 一次同步只允许查一次，整批失效与量高共用同一份列表。
- **判定有没有真的修好**：不要用「感觉快了」。用 CDP `Performance.getMetrics` 看 `LayoutCount` / `LayoutDuration`，或开 `Tracing`（`devtools.timeline`）数 `Layout` 事件次数。修好的判据是 **Layout 次数为 1**，而不是耗时减半——一次 173ms 的 Layout 是新建 500 行 DOM 的固有成本，优化不掉。
- **回归**：`scripts/workbench-layout-sync.test.js`（14 项）用计数假 DOM 把强制布局次数变成可断言的事实，锁住上述四条边界。

### 2. 审核轨迹的展开/收起在筛选、翻页、改每页行数后回弹
- **现象**：用户手动收起某一行的审核轨迹，一旦触发重渲染（筛选、翻页、改每页行数、AI 结果到达），它又弹回默认展开态，只能反复点。
- **根因**：重渲染会重建全部行节点，`renderNoteSummary` 每次按 `isNeedsCheck` 重新算默认值，DOM 上的 `hidden` 被整体冲掉。展开状态不是备注数据，不能落盘，但在会话内必须记住。
- **修复**：用户开合选择记在 `pipelineOpenOverrides`（`setPipelineOpen` 写入，`pipelineDefaultOpen` 读取）；没被手动开合过的行仍走默认（待判行展开，普通行收起）。
- **注意**：这类回弹不只是体验问题——用户每重开一次就要再点一次，而每次点击都可能连带一次重渲染，这正是「越点越卡」的放大器。
