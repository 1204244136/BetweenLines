# BetweenLines

BetweenLines 是一个面向长篇文本的本地分析工作台。它把 EPUB、TXT 和其他文档中的正文整理成稳定、可追溯的段落与派生行单元，再由不同的领域工作台进行翻译比较、校对或叙事分析。

## 文档范围

本 README 面向使用者、评估项目的协作者和希望运行现有工作台的开发者，说明项目是什么、当前支持什么、如何安装运行，以及结果保存在哪里。

编码代理和维护者还必须阅读 `AGENTS.md`。模块归属、数据不变量、产物字段与模式裁剪契约、生成物边界、修改纪律、故障定位和验证清单都以 `AGENTS.md` 为准，本 README 不重复维护。

项目的重点不是把所有 AI 功能塞进一张表，而是建立一条可以被多个分析任务复用的文本基础设施：

- 格式转换、正文过滤和段落索引只做一次，保留原文的结构边界。
- 每个分析任务拥有自己的数据模型、提示词、缓存和工作台，结果不会互相覆盖。
- 句子或对话行是段落之上的派生视图，不会替换完整段落，也不会破坏翻译对齐的不变量。
- 输入、模型调用和生成物默认留在本机；项目快照可重复生成，源文本和个人路径不会提交到仓库。

## 工作台

### Translation Compare

当前实现是原有的 TransComparator 工作流：一份原文加一到两份同级译文/版本文本，经过正文过滤、跨语言对齐和非原文差异比较后，生成 HTML 工作台、CSV 和 JSON。

- 原文是准入边界：译本里的特典、附录、版权页、后记、译注等，如果原文没有对应内容，就不进入最终比较。
- 一到两份非原文是同级材料。程序内部可以选择技术 pivot，但这不代表任何译本更权威。
- 原文段落保持完整，只有非原文可以为了对齐、diff 和展示进行拆分或合并。
- 产物只包含所选模式真实存在的列。切换到双语模式（原文 + 一份译文）后重新生成，工作台、CSV、JSON 和发给模型的提示词都只描述两列；行签名和项目标识不因这次裁剪而变化，已保存的备注仍然对应原来的行。

#### 工作台控制区

控制区在表头与表格之间，由四个折叠抽屉组成，按数据流方向自上而下排列：

1. **预筛选**：跑规则/相似度粗筛，产出预筛结果。
2. **AI 辅助校对**：对未通过预筛的行做语义细筛，产出 AI 评分与结论。支持保存、切换、更新与删除「AI 模型预设」，切换不同模型（如本地 Ollama 与不同第三方兼容服务）时无需重复填写接口、地址、模型名称、API Key、推理强度、并发度与智能并发配置。
3. **筛选与批处理**：按机器产出筛出要看哪些行，控制原文/译文差异/修改差异等列的显隐，并对当前筛选结果批量确认或写回（写回会改原文件）。
4. **备注空间与找回**：浏览器本地备注的备份、迁移与历史找回。

这四个抽屉外面套了一个父抽屉「控制面板」，可以一键把整组收起或展开，适合放手让机器跑任务、只想看表格的时候。父抽屉默认展开，摘要行显示当前已展开几个抽屉（例如「已展开 1/4 项」）。

四个抽屉默认全部折叠；点摘要行右侧的箭头展开。「筛选与批处理」里筛选条件在最上、显示开关居中、会改源文件的批量按钮单独成组放在最后并有分隔线隔开，避免误点。每个抽屉的摘要行会带实时状态。

#### 操作回执与浮动提示

按钮和控件的一次性结果走右下角的浮动提示（Toast）：批量确认与写回的结果、预筛或 AI 校对跑完的统计、刷新模型列表、模型预设的保存/切换/更新/删除、备注空间的备份/导入/找回/清空、行内「未校验」核验、恢复默认提示词都会弹一条回执。这些回执原先写在 AI 抽屉里的状态行上，而抽屉默认折叠——点了按钮常常看不到任何反馈。提示按语气分色（中性、成功、需要留意、失败），右上角可以手动关闭，到时自动消失；同一条消息连续出现只保留一条，最多同时显示 4 条。说话人归属工作台用的是同一套浮动提示，两边的语气、停留与去重规则完全一致。

出错提示（写回失败、接口报错等）会比其他提示多停一会儿：这类消息最长，按常规时长折半会读不完就消失。

改动源文件的不可逆操作都会先弹一个页内确认框，写明条数、影响范围和备份状态（写回原文件、清空本页备注、清空历史空间、删除历史空间、从备份登记，以及控制台的删除项目）；需要留意的是，**确认框里的备份状态就是你当前的设置**——默认关闭自动备份时写回会直接改写原文件，建议先在设置里打开备份或自行留档。

需要一直看得见的机器状态仍留在固定位置：AI 与预筛的运行进度、跑完的统计、未连接本地控制台服务的提示、被跳过或忽略的结果汇总都在「AI 辅助校对」抽屉的状态行里；备注空间的面板内也保留一行就地状态，和空间列表挨着读；本地存储写失败或未保存的警告固定显示在备注面板中，不会自动消失。

### Speaker Attribution

说话人归属工作台用于根据上下文确认“这句是谁说的”。它只处理带 `「…」` 或 `『…』` 的完整发话；引号中的多个句子保持为同一行，叙述行只作为上下文而不生成判断项。

它支持单语输入；双语输入会先进行预对齐，并保留对齐证据较弱和未匹配的行供人工复核。两份输入都是 EPUB 时，工作台会先按章节表头分段，再在同一段内做行级对齐，避免目录、封面、版权页和后记占用正文的对齐位置；没有共同表头时才退回整篇对齐。

生成的工作台提供分页、搜索、按判断/对齐状态筛选、归属证据与上下文查看、当前行 prompt 复制、浏览器本地自动保存和确认结果导出，不会一次性渲染全部行。对照列和“主文本对照”开关只在双语输入时生成；单语工作台的数据文件里不会出现任何对照字段，也不显示对齐版本概览。

每行的“归属证据”是确定性启发式给出的审阅优先级，不是正确率：它按邻近叙述里的说话动词、引用式 `と、Xは…` 和疑似称谓排序，把有明显可辨识证据的行提到高/中，把只能靠对话轮次推断的行标为弱，最终仍需人工结合上下文判断。双语模式下的“对齐证据”标签只反映跨语言结构信号的强弱（共享片段、数字、句末结构、长度），不把字符重合当作语义结论。

说话人结果不作为翻译备注，也不直接加成翻译比较表的一列；它使用独立的分析类型、结果模型和缓存身份。

说话人工作台的模型列表通过本地控制台服务获取，使用时需保持控制台运行。复制正文或当前行 prompt 失败时，页面会提示手动选择文本复制。

## 共享管线

```text
输入文件 -> Pandoc/EPUB 转换 -> 正文过滤 -> 完整段落索引
        -> 派生句子/对话行（带 parentParagraphId 与源文本偏移）
        -> 领域工作台分析 -> 独立的 HTML / JSON / CSV 结果
```

当前翻译比较仍然使用完整段落和跨语言对齐；派生行单元只为未来的句子级分析提供共享入口，不会改变现有段落编号或 alignment 语义。

## 环境要求

- Node.js 18+
- Python 3.12+
- Pandoc（非 TXT 输入默认需要；EPUB 在 Pandoc 不可用时可回退到内置 reader）
- 可选：支持 CUDA/ROCm 的 PyTorch，用于跨语言对齐
- 可选：Claude、OpenAI-compatible 或 Ollama 本地接口，用于 AI 校对

## 快速开始

```powershell
npm run setup:env                    # 首次初始化
npm run setup                        # 启动本地服务
```

Windows 上也可以直接双击仓库根目录的 `start-setup.bat`：它等价于 `npm run setup`，并在本地服务开始监听后自动打开控制台页面；服务未就绪时不会提前打开，因此不会看到「拒绝连接」的错误页。

GPU 环境可先检测并安装匹配的 PyTorch：

```powershell
npm run detect:accelerator
npm run setup:accelerator
```

需要跳过安装项或重建虚拟环境时：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/setup-env.ps1 -NoInstallPython
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/setup-env.ps1 -RecreateVenv
```

没有 GPU 时可以显式允许 CPU 对齐：

```powershell
$env:TRANS_COMPARATOR_ALLOW_CPU = "1"
npm run align:jp
```

在浏览器打开终端显示的地址（通常是 `http://127.0.0.1:4317/`），为每个角色登记本机文件或解压目录，保存选择后点击“生成”。单个文件支持 EPUB、TXT、DOCX 等格式；解压目录必须是单本书的根目录，并包含 `META-INF/container.xml`。控制台会校验文件类型与 EPUB 结构；系统选择窗口不可用时可粘贴本机路径。双语模式中 `A` 是原文、`B` 是非原文；三语模式中 `A` 是原文、`B` 和 `C` 是两份同级非原文。

### 命令行

也可以不使用控制台，直接按步骤运行：

```powershell
npm run check:pandoc                 # 检查 Pandoc
npm run export:paragraphs            # 转换并导出段落
npm run align:jp                     # 检查加速环境、导出并跨语言对齐
npm run build                        # 构建当前翻译比较工作台
npm run align:jp && npm run build    # 完整流程
npm run build:speaker                 # 构建说话人确认工作台
npm test                             # 运行 Node 测试
```

命令行可从目录推断输入，也可以显式指定文件或 index-X 作品编号：

```powershell
npm run export:paragraphs -- --input-dir "C:\path\to\texts"
npm run export:paragraphs -- --jp "C:\path\source.epub" --cn "C:\path\version-a.epub" --tw "C:\path\version-b.epub"
npm run export:paragraphs -- --work-id S1_01
```

配合上游 `index-X` 项目（同级目录 `../index-X`，或用 `INDEX_X_DIR` 指定）时，脚本会自动解析简中译本与日文原文，并支持该项目的正文格式契约（L1-L6 行模板、`heading-lines` 标题、`ruby` 注音、`noteref` 译注标记、引子/尾声章节结构）。具体的作品编号、文件命名与章节边界规范见 `AGENTS.md`。

简介与彩页之后、序章之前的无标题引子会保留在正文中。旧项目若出现开头缺失或两种语言从不同情节开始，需要重新执行导出、对齐和构建；仅刷新或应用新布局不会修复已生成的对齐数据。

若 Pandoc 不在 `PATH` 中，设置 `PANDOC_BIN` 指向 `pandoc.exe`。运行时数据目录可通过 `TRANSCOMPARATOR_DATA_DIR` 覆盖。

## 输出与隐私边界

生成物只写入 `out/projects/<projectKey>/snapshots/<snapshotId>/`，这是已发布结果的唯一事实来源。`out/runtime/` 和 `out/.staging/` 只保存当前输入、未发布的生成任务和临时工作目录；顶层 `out/active-project.json` 是当前活动项目的小型指针。`out/` 默认不提交到 Git，项目快照可重复生成。

项目默认保留最近两个快照。备注保存在浏览器 `localStorage`，不会写回源文本；不同分析结果分别保存，切换工作台不会互相覆盖。

控制台的「已生成项目」支持切换、应用新布局和删除。应用新布局会基于当前快照在隔离目录重新渲染，并发布成一条新快照后切换活动指针，不会原地覆盖旧快照。删除会永久移除 `out/projects/<projectKey>/` 下的快照与工作台页面，无法恢复；删除当前项目后会自动切换到最近保留的另一个项目。源文本、已登记的输入选择和浏览器备注都不受影响，可以重新生成同名项目。

提交前确认以下内容没有进入版本控制：`.venv/`、`node_modules/`、`out/`、`.codegraph/`、源文本、模型缓存、绝对路径、API Key 和其他本机临时文件。

## 预筛选与 AI

翻译比较的预筛选是独立的确定性步骤：先统一繁简、全半角、空白和不可见字符，再对满足条件的正文计算相似度，只把仍需判断的行交给模型。AI 结果写入当前翻译比较快照对应的备注空间，人工备注和人工确认优先。

预筛结果属于整个项目，不属于某一次打开：重新打开页面（或重新生成工作台）后，页面会从本地服务认领上一轮预筛的结果，已人工确认的行不会重新出现在「待确认」里，`确认预筛` 也仍然可用。点「开始预筛」时，已经勾选「人工确认」的行会作为已处理跳过，日志里的「人工确认跳过 N 行」就是它们。

通过 `npm run setup` 启动的本地服务支持 Claude 原生 Messages API、OpenAI-compatible 服务和 Ollama 等本地接口。三语模式可选择校对 B 或 C，双语模式只校对 B；EPUB 注释标记（`noteref`）会原样保留，不参与翻译语义判断。请求参数按模型自动适配：推理模型只发送其自己声明的思考档位，不支持 `temperature` 的模型不会附带采样参数，非推理模型仍使用 `temperature` 调整。

AI 校对带有自动熔断保护，由程序内部决策，页面上没有阈值或开关可调。两类情况分开处理：接口真的在报错（5xx、超时、断连等）时，最近 20 次调用中失败占比达到 50%（累计满 10 次结果后开始判定）就自动终止任务，避免继续白花钱；上游持续限流（HTTP 429、503、529）时不会直接终止，而是暂停该阶段、按 20 秒 → 60 秒 → 180 秒逐档冷却后再试探，试探通过就自动恢复，三档都仍被限流才终止，已完成的行会保留，可用「继续剩下的」接着跑。接口配置或响应异常（如 401、返回非 JSON）仍会立即终止。三个阶段各自独立判定，终止原因会写明是哪个阶段。

AI 校对支持「智能并发」自适应调节：在「校对设置」勾选「智能并发」后，默认以初始并发数 3 启动任务；当连续请求正常（默认连续 5 次成功）且间隔平稳时，调度器自动逐步上探（每次 +1）直至设定的并发上限（默认 10）。当遇到第三方 API 频控或并发限制（HTTP 429、503、529，或返回速率与过载相关报错）时，调度器会自动下调并发数并进入自适应退避窗口（自动识别并遵循响应头里的 `Retry-After`），对受限行执行最多 3 次自动重试，重试期间不计入熔断错误——**这一层不受「智能并发」开关影响**：关闭它只是不再自动上探（并发数固定），频控退避与单行重试照常生效。初始并发数与并发上限均支持在面板中灵活修改（范围 1–32），并随项目配置、模型预设或本地基准一同保存，跨项目切换互不污染。

AI 校对可以串成三级流水线：**阶段一 事实初审**逐行判断事实性硬伤，**阶段二 文学复审**复核初审提出的修改，**阶段三 终审仲裁**裁决初审与复审的分歧。每个阶段在自己的卡片上单独选择模型预设，不填代表不启用；阶段三需要先启用阶段二。

三个「开始」按钮只表示**起点**，往下走到哪一段由配置决定：配了阶段二就从初审接到复审，配了阶段三就再从复审接到仲裁。点阶段一「开始」＝「初审 →（配了复审）复审 →（配了仲裁）仲裁」；点阶段二「开始」＝「复审 →（配了仲裁）仲裁」，用来对已有初审结论的行补跑复审；点阶段三「开始」只跑仲裁。三个阶段在**同一个任务里流水线推进**：初审完一行立刻移交复审、复审出分歧立刻移交仲裁，各自并发、各自退避，不必等前一阶段整体跑完——所以「阶段二等阶段一全部结束」这种空转不会发生。流水线运行时三个「开始」按钮都会禁用（无法中途插入单阶段），三个「停止」按钮都可用（停的都是同一条流水线）；任务结束会回报「流水线已完成：初审 → 复审 → 仲裁」。想只跑一段，就把它的下游设为「未启用」。

**已有初审结论、只差复审的行不会重跑初审**：点阶段一「开始」并在确认框里选「继续剩下的」时，它们直接进复审队列，和初审刚产出的行走同一套并发——「待复审 800 行」会立刻按你配的复审并发跑起来，而不是等初审把它们一行一行重新产出。

两个自查点：仲裁或复审调用失败的行会如实计入卡片上的「异常」，不会被静默丢掉（修好之前它们既不算定案也不算异常，看起来就像"处理了很多行但定案数不动"）。失败也不会无限刷下去：模型名/接口地址/密钥这类**配置类致命错误会当场终止任务**，其余连续失败由**按阶段隔离的自动熔断**拦下（最近 10 次里失败过半即终止；持续限流则先冷却探测，终止原因会写明是哪个阶段）。如果阶段三卡片显示「**未接入**」，说明这次任务启动时没有接入仲裁——启动时阶段三预设还没配、或者那个预设已失效；停掉任务、确认阶段三预设后重新启动即可（**点阶段三「开始」不会**再显示「未接入」，那时仲裁本来就在跑）。如果页面弹出「**控制台服务未更新**」，说明常驻服务还是旧版，重启 `start-setup.bat` 后重新启动任务。

提示词按职责分层，合并后一起发给模型；**层不重复说同一件事**，同一条判据只写在它该在的那一层：

- **通用侧**是所有作品都成立的校对任务契约：判断顺序、证据优先级、最小改动、修订文本边界（含"行序与行边界由对齐决定"）、上下文与输出评分口径；其中片段处理、noteref 语义与原文外内容只在当前行出现对应现象时注入。
- **模式层**只讲当前比较模式的列语义与结论字段（双语是 A/B，三语是 A/B/C），因此双语产物里不会出现 `counterpart` 这类词。
- **特化侧**是可替换的规范档案（`src/workbenches/translation-compare/ai/profiles/`），描述具体工作阶段里哪些转换不算缺陷、哪些才算缺陷。仓库自带两份：`novel.js`（与作品无关的小说成品规范：以发布成品为 B、日文原文为 A，语序重排、断句、全角标点与直角引号、注音与傍点转排版标记、竖排通信标识转横排方向、连接词用破折号衔接等都属于正常工序；违反规范如省略号打成连续句号、「！？」顺序与数量不符、该注音未注音、术语不统一才判缺陷；引号/括号内侧的句末点号则相反——日文原文常在收尾符号前省略它，译文按中文规范补出不算缺陷、把它删掉才算；引号的有无本身也不是缺陷——中文成品用「」/『』标记被提及的词、心声、拟声与招牌，日文原文在这些位置常不加引号，仅凭原文没有引号不得判译文「误加引号」（同一卷里这种形状有二十多行）；反过来，标记内只是一个词或短语时，句末点号落在标记**外**侧才是常规写法，`「战地医院」。` 不该被改成 `「战地医院。」`；同一套写法规范也约束 AI 自己给出的修改结果——半角标点会被要求改成全角，弯引号与直引号也要改成直角引号）与 `demo.js`（作品专有档案的公开示范，同时是本项目实际使用的一份，只补译名口径与角色语言特征）。
- **动态上下文**只在该行/该章/该轮命中时才注入，共五段：对照表命中的术语、本章的说话习惯、说话人判断、低分归因（极低分那一轮给它的相邻行与归因口径），以及线上查证（模型判不了那一轮给它的官方站点入口 + 要查的词条）。五段都先剥掉自定义提示词里的旧段再注入，任何路径都只会出现一份。说话习惯段还额外**按行收窄**：章级判定仍然回答"这一章出现了哪些角色"，但某一行只拿到"本行提到了他、或本行原文出现了他的口癖"的那些角色规则——一行没提到本章任何角色时整段不注入，页面上"本章命中角色/特色流失"的结论不受影响。
- **固定尾巴**是 noteref 保留约束、整卷术语表与 JSON 输出约定，永远全量——这几条宁可重复也不省。

另外，日语常用“短式先现 + 下一行同头重写”来承接感情，例如原文 `それは。` → `それはとても…`，目标列 `虽然。` → `虽然那只是…`。这种情况下基础轮会主动带上下一行一起判断，并明确把本行视为上下句递进装置，避免把 `それは / 虽然` 当成独立指示代词或让步连词改译；AI 仍只输出当前行的修改结果，不会把下一行并进来。这个跨行判定只在检测到同头重复时启用，普通行不会因此多带上下文。

提示词里有一批规范**只在特定的版式、文字现象或上下文条件下才有意义**：特化侧包括注音、傍点加粗、译注标记、分页与图片、空行折叠、省略号写法、「！？」顺序、引号用途（含「原文没写引号不得判译文误加引号」的证据边界）与成对标记（引号/括号）内侧句末点号的位置、方向敏感的通信标识与箭头、连接词衔接、拟声词与语气词、数字与单位；通用侧包括片段、noteref 语义和原文外内容；角色口癖与说话特色则只随命中的动态说话块出现。它们会跟着当前行的原文与译文按需注入：一行普通叙述不会背上"注音该怎么标"「傍点怎么加粗」或某个角色的口癖规则，而真的出现对应现象时规范立刻补上。任务是语义判断的规则（遗漏信息、否定时态、译名一致性、作品专有写法、证据边界）仍每行都在；探测不出结论时一律按"命中"处理，宁可多花 token 也不丢规范。任务结束的日志会汇报本次省掉了多少条、平均每行省多少字符。页面与「校对设置」里预填的默认提示词仍是档案的全量正文，人工读得到完整规范。另外，模型给出的修改结果里如果混进了原文（日文）的文字或读音，程序会作废这条结果并把它标成待人工确认——这类文本会被「写回」直接落进成品，所以宁可交人工处理，也不让它过去。

还有一类规范**只对某个角色或专有词成立**——她的假名改写习惯、他的编号写法、某件装备的固定写法。这类条目可以在档案里用 `characters` 声明适用范围（`{ characters: ["甲野一郎"], features: ["numeric"], text: "…" }`），只有当**这一行真的出现那个名字**时才注入，没出现的行不会背上别人的专属规则；需要放宽到姓氏之类的片段时写成 `"甲野一郎|甲野"`（片段会连带命中同姓的别的角色，慎用）。`features` 与 `characters` 可以一起写，此时两个条件都成立才注入。声明名单只能由档案给出，程序不认识任何作品设定；名单写错或写窄时，任务日志里的「因本行未出现该名字而省掉 N 次」就是排查入口。**角色相关的规则优先写进说话习惯表**（见下），那里自动按角色名与口癖判定，不必逐个开 `characters` 条目。

在「校对设置 → 特化规范」里切换档案；自定义提示词只会补上缺少的那一层，不会把整段规则重复追加。接自己的作品就复制一份档案改 `id`/`name` 与最后那一节；不想公开的档案可以放进被忽略的 `profiles/local/` 目录，或用环境变量指向仓库外的文件：

```powershell
$env:TRANSCOMPARATOR_PROFILE_FILES = 'D:\my-profiles\work.js'   # 多个文件用 ; 或 , 分隔
```

如果自己的档案只是"某份既有档案 + 本机专有的东西"，不要另立一份：用 `extends` 叠加，只写差异字段。注册表会把差异合并进基底并**沿用基底的 id**，所以下拉里仍然只有那一项，不会出现两份逐字相同的规范让人分不清该选哪个，也不会因为选了另一份而静默丢掉下面声明的表；基底以后改了规范，这里也自动跟上。

```js
// profiles/local/work-profile.js：让"某系列成品"这一项带上本机的两张表
module.exports = {
  extends: "demo",                        // 叠加到内置示范档案上（沿用它的 id、规范正文）
  name: "我的作品（本机档案）",             // 只声明要改的字段：名字、摘要、补充小节、表
  termTables: ["D:\\tables\\译名对照表.xlsx"],   // 也支持 csv/tsv/json；可用 TRANSCOMPARATOR_TERM_TABLES 追加
};
```

叠加规则：`name`/`summary`/`speechHabitScope` 声明即覆盖，未声明沿用基底；`sections` 按小节标题追加，标题与基底重名时替换基底那一节；`termTables`/`speechTables` 与基底的合并去重（基底的表继续生效）。`extends` 只能指向已注册的档案，指向不存在的 id 时只告警并跳过（不会凭空造出一份档案）。

对照表按表头识别列（`Base_Ori` 原文、`Ruby_Ori` 读音、`Base_Trans` 本项目译名、`Ruby_Trans`/`Other_Fandom` 英文与其他译法、`Type`、`Memo*`）。原文列里的 `【】` 只是用来标记**读音加在哪里**（`Ruby_Ori` 按逗号顺序对应各个方括号里的文本，如 `【御坂】【美琴】` + `みさか,みこと`），正文与成品里几乎不会出现方括号，所以匹配和显示都用去掉方括号的原文。

xlsx 里的文本即使被整表转义成 `&#39764;` 这种数字字符引用（有些导出脚本会写成纯 ASCII 的 XML），读取时也会解回真实字符，不需要重新导出。

选好特化规范后，「校对设置」里会显示一行对照表状态——`未声明` / `文件名（N 条术语）` / `加载失败`，鼠标悬停可看完整路径与错误，用来确认表到底有没有生效。项目快照与工作台页面里只记录表的**文件名**（对照表与说话习惯表都是），本机完整路径只出现在这个状态提示、运行日志和离线脚本报告里，页面可以直接分享。

对照表的作用是**给模型提示该用哪个译名**，只有一种情况会跳过模型：这一行的有效内容本身就是术语（例如单独一行的 `御坂美琴`），对照表能给出完整结论。句中还有别的词时，术语一致只能说明术语用对了、说明不了整句翻译没问题，这一行照常交给模型，对照表以提示词形式注入。判定规则是保守的：

- 整行有效内容都是本项目术语（术语之外只剩句读）→ 直接判为一致，**不调用模型**（这是唯一跳过模型的情形）；
- 术语一致但句中还有别的词 → 不写结论，把命中的术语与标准译名注入提示词，整行仍由模型判定；
- 译文里出现的是对照表登记的“其他译法/英文写法/字形差异”，或整条术语没在译文里出现 → **同样不算结论**：把「原文 → 项目译名（译文现用某某写法）」当线索注入提示词，由模型结合整句判断该不该改、改哪里，并在结论里写明依据。术语判断是模型分析里的一个环节，不是先于 AI 的终局判定；
- 命中的是短词（2 字）、读音或分段 → 只记录证据，不据此判缺陷、不臆造替换；满 3 字的基文别名才够格指控译名差异（门槛放宽到 2 字试过一轮，实测假差异偏多，已回到 3 字）；
- 命中的是**假名写法**（`グループ`、`メンバー` 这类）→ 对照表**不下结论**：同一个词在有的场景就是普通词（「处于顶级的集团」），在有的场景确指那个组织（暗部 GROUP），删条目会丢掉真实场景、由对照表定论又会误报，所以把它作为提示注入，由模型结合上下文判断该不该用这个译名（判断结果连同术语标签一起写进备注，人工核对结论）；
- 条目**在表里写了读音/别名**（`Ruby_Ori` 非空，且不是人名）→ 要**原文与译文两侧都出现该词的注音形态**才算「表里那个专有名词」：原文侧要连着那个读音一起出现，译文侧要把注音落在这个中文译名上、或注音内容就是表里那条读音。只满足一侧（或两侧都没有）时**降级为「只作一致性证据」**：译文确实用了本项目译名时仍算命中（一致 → 可注入提示词、可跳过模型），译文用了别的写法时**不算命中、也不指控**——宁可不判，也不凭一次字面命中去报译名错误。同一个汉字词在正文里常常是普通词义：表里的 `発信機` 指的是学园都市那件装备（注 `ナノデバイス`），而正文里的「ＧＰＳ発信機」就是发射机，只对上基文就报“译名不一致”是误报。人名不受这条约束（原文里的人名只在首次出现时注音，之后一律不带）。之所以要两侧一起看：表里那一列混着两种东西——**特殊别名读音**（`発信機/ナノデバイス`）与**这个词本身的普通读音**（`魔術/まじゅつ`、`学園都市/がくえんとし`），后者在正文里永远不会带注音，只看原文侧会把它们整体排除，模型拿不到「魔術 → 魔法」这条提示，就会按通用词典判成「魔术」。运行日志会如实报出两类数字：有多少条候选因证据不足、且译文未用该译名而未参与判定，有多少条降级为只作一致性证据，方便判断规则是不是过严。

**生成工作台时就会先算一遍对照表**：页面在跑任何 AI 任务之前，已经给命中行标好徽标——`术语冲突`（译文写法与项目译名不一致，或整条没译出来；这一行照常交给 AI，冲突作为线索注入提示词）、`纯术语`（整行都是术语，跑预筛时不会调用模型）与 `术语注入`（术语一致但句中还有别的内容，仍会交给模型，术语作为提示词注入），并在同一行给出 `术语 N` 的小标签：点开就能看到这行到底命中了哪些术语（`原文 → 译名（类型）`，鼠标悬停也能看全）。术语标签与给模型的提示词用的是同一批条目，只列**这一行确实用到**的术语（只出现姓氏、或只是读音撞车的条目不进列表，避免同姓角色互相牵连）；跑之前标签标「预判」（构建期判定），跑之后标「结论」（备注里的真实结论），所以人工可以随时核对“模型是按哪几条术语判的”。**术语冲突行不会被相似度预筛挡掉**：这类行的术语判断必须由模型给出，否则“看起来差不多”就会把术语问题一起放过。面板上的对照表状态还会顺带给出预筛数字（“构建期预筛 678 行命中（整行只有术语、跳过模型 17；其余 661 行注入术语后交给模型，其中术语冲突 30 行），预计 3102 行仍需 AI 判定”）。跑任务时程序会重新逐行判定（结果要带当次的目标列与标签），并把它与构建期结论对照：一致就在日志里明说，对照表在构建之后被改过则提示重新构建工作台。

想先看命中情况再决定花不花 token，可以不启动服务直接跑离线脚本：

```powershell
node scripts/term-prefilter.js --profile demo --limit 20     # 只列术语冲突的行（结论由 AI 给出），并对照构建期结论
node scripts/term-prefilter.js --profile demo --from-snapshot # 只读构建期落盘结论（与页面徽标同源）
node scripts/term-prefilter.js --profile demo --all --json --out report.json
```

### 低分归因层（先解释为什么低分，再动手改）

逐行看时，极低分长得都一样——"整行与原文无关""像凭空多出来的台词"，但原因不同、修法也不同：整行译文与相邻行**互换了**、这一行只是上下句的一半、代词与省略主语要靠上下文、真的把否定或时态弄错了、译文自己加了原文没有的话、原文本身晦涩被误判……

所以扣分达到阈值（默认扣 60 分以上，等价 40 分以下）的行不会直接被当成"逐句误译"，程序会**再问一次**，并把这一行前后各两行的原文与译文配对一起给它：

- **先归因、再修**：结论必须说明这一行为什么扣这么多分（跨行错位、对齐切分、依据不足、语义硬伤、内容遗漏或增译、术语、表达层、原文风格、其实无需修改……），再按这一类原因修。备注的**分析栏**里会写出原因，例如 `低分归因：本行译文实际写的是**下一行**的内容（跨行错位），已保持原文行序、按本行原文重写`；复核后认为本来就不该扣这么多分的，会如实把结论改成"无需修改"。（归因与查证说明都写在分析栏，不会混进「修改结果」——那一栏就是会写回成品的文本。）
- **跨行错位是必查项**：这类缺陷在逐行视角下必然表现为"整行重译"，最容易被当成逐句错译，所以先核对相邻行的原文/译文配对，两个方向都看（本行承接了下一行，或上一行的内容落到了本行）。
- **原文行序不动**：行序与行边界由日文侧对齐给定，不属于语言质量问题。错位只能按"本行原文该译成什么"来修——程序不会建议把相邻两行的译文对调，也不会把邻行译文或两行内容糅进一条修改结果。
- **不够就继续要上下文**：现有相邻行不足以归因时，模型会继续索取相邻行，程序一轮一轮往外补（仍受上下文行数与字符预算限制）；宁可多问一轮，也不产出编造的译文。确实判不了就转人工确认。
- **首行与末行**没有可核对的邻行，直接跳过这一层。
- 阈值与窗口可调：`lowScorePenalty`（默认 60，等价 40 分以下；想让"较差"整档都归因就调到 45）、`lowScoreRows`（默认 2，前后各几行）；关掉这一层传 `lowScoreCheck: false` 或设 `TRANSCOMPARATOR_LOW_SCORE=0`，阈值也可用 `TRANSCOMPARATOR_LOW_SCORE_PENALTY` 指定。任务日志会汇报本次复核了多少行、其中多少行归到跨行错位、原因分布如何。

### 线上查询层（模型判断不了时，按顺序查三个官方站点）

像 `グループ` 这种命中的是假名写法的存疑行，会先交给模型判断；如果模型说判断不了、相邻行也补过了，程序会**按顺序**去查官方资料——**拿到能定论的关键信息就立刻停**，人工只接受结果，中间不需要任何转述。整条判定顺序是：对照表（离线）→ 模型 → **低分归因（只对极低分行：先解释原因再修）** → **线上查证（中文 → 日文 → 英文 → 自行检索）** → **成品格式门禁（一行就是一个成品段落：并回模型插入的换行与空行、去首尾空白）** → **标点规范化（中文全角、英文句子保持半角，双引号统一成直角引号，并补回被删掉的成对标记内句末点号）** → **输出语言护栏（修改结果里混进原文文字就作废、转人工确认）** → 待人工。

成品格式门禁也是结论产出之后的确定性工序，治的是**模型看错了行结构**：一张表格行只对应一个原文段落，段落结构由目标列那一行给定，**原文那一侧的分行、空行、行首缩进都是版式事实，不是译文缺陷**。真实回归：旧对齐曾把两个原文段落合成一张表格行（页面上换行渲染成空格，人眼看不出来），模型据此把换行写进了修改结果；现在原文侧在生成对齐时就保持一段一行，旧快照里的同数量多段组也会在构建时拆开。模型仍可能自行插入换行（含 `<br>` 与空行），这类换行会被并回本行，并在备注分析栏留痕（`格式自动规范化：删除模型插入的换行 N 处`）；而**段数与目标列对不上**、或**译注标记（noteref）比目标列多/少**时，因为无法确定性还原，那一行的修改结果会被作废并转人工确认（原因写在备注里）。改了什么会写进备注、任务日志汇报总数。关掉它：跑任务时传 `formatGuard: false`，或设 `TRANSCOMPARATOR_FORMAT=0`。

标点规范化是结论产出之后的确定性工序：模型的修改结果里，中文语境的半角标点会被统一成全角（`，。？！；：（）`，省略号统一成 `……`），**整段英文句子里的标点保持半角**（数字 `3.5`、缩写 `e.g.`、URL、代码里的标点一律不动）。中文语境里能确定配对的双引号也会统一成直角引号：`“咔哒”` 或 `"咔哒"` 会写成 `「咔哒」`；英文整句里的直双引号保持原样，残留的弯引号则作废该条修改并转人工，不把未知配对关系猜进成品。另外，中文规范要求完整句的句末点号落在引号/括号**内侧**，而日文原文常在这个收尾符号前省略它——模型把译文本来就合规的点号判成「多出句号」删掉时，程序会把那**单独一个**点号补回来（`（……变成那样。）`、`「……报告道。」`；成对的多余点号 `「。。」`、行尾或句中的点号不在这一层）。改了几处会写在备注的分析栏里（`标点自动规范化：半角→全角 N 处`、`弯引号/直双引号→直角引号 N 处`、`补回引号/括号内的句末点号 N 处`），任务日志汇报总数。关掉它：跑任务时传 `punctNormalize: false`，或设 `TRANSCOMPARATOR_PUNCT=0`。

- 站点在特化档案的 `wikiSites` 里**按顺序**声明（示范档案已带中文灰机、日文 atwiki、英文 Fandom 三个入口；换作品改这一行），可用 `TRANSCOMPARATOR_WIKI_SITES` 覆盖；**没声明站点这一层不启用**。
- 一轮只给**一个**站点入口 + **要查的词条**（本项目译名优先、原文写法备选），**不给直达词条链接**——条目名一旦猜错就是个打不开的地址，模型只会照着瞎猜；给入口加词条，让它自己在站内找，找得到才算有依据。
- 挨个来：这个站点查不到（打不开、搜不到、内容与问题无关）就自动换下一个；一旦拿到能定论的关键信息就**立即**给结论并停止，后面的站点与“自行检索”那一轮都不再发。
- 三个站点都不行 → 让模型**自行检索**（浏览器、搜索引擎，或它确实掌握的可信资料）；还是不行 → 转人工，备注里写清完整轨迹：`已依次尝试 中文（灰机） → 日文（atwiki） → 英文（Fandom） → 自行检索，均未获得有效内容，转人工确认`。
- **不许凭记忆猜**：每一轮都写明“只依据你实际查到的内容；打不开、搜不到、内容无关都不要猜，本轮照常返回无法判断”。最坏情况是多问几轮后落到人工，不会多出一个编造的结论。
- **本机不抓取网页**：实测这些站点对本机的请求一律返回 403 风控挑战页（换 UA、换客户端都一样），绕过它需要浏览器 cookie 或浏览器引擎；本机只负责“按什么顺序、给哪个入口、问什么、什么时候停”。
- 关掉这一层：跑任务时传 `webLookup: false`，或设环境变量 `TRANSCOMPARATOR_WEB_LOOKUP=0`。任务日志会汇报本次有多少行走查证、一共问了几轮、其中多少行据此得出结论。

（`--profile` 用档案 id，也就是叠加时 `extends` 指向的那个 id：内置示范档案是本机的叠加基底，所以本机的表也算在 `demo` 这个 id 下。）

### 说话习惯层

第二类辅助数据是**说话习惯表**（角色 / 口癖 / 类型 / 本项目 X版写法 / 网翻 / 台版 / 备注 / 小说首次出现），在档案里用 `speechTables` 声明。它解决的是"刻意写法被当成翻译错误"，以及"原文有口癖、译文没译出来"：

- **示范档案的表已经内化**：`ai/profiles/demo.js` 自己就声明了这张表（`speechTables: [require.resolve(__filename)]`，文件里的 `entries` 是外部表格转成的 52 条数据）——运行时不再挂外部 xlsx，改条目直接改该档案，构建后生效（运行期按该文件的修改时间校验，被改过会提示重新构建工作台）。想临时叠加自己的表（例如试验新口癖），在 `speechTables` 里再加路径或用环境变量 `TRANSCOMPARATOR_SPEECH_TABLES` 指向仓库外的表格即可，两张表会合并生效；同一角色在两处都登记会各出一条规则，实验完记得删掉。
- **当前项目按 X版 对齐，X版写法是"特色流失"判定的唯一基准**：`-` 不是“忽略”，而是明确的不特殊处理。这类条目仍会进入命中行的提示词，并硬性要求不得采用网翻版或台版写法；它们不参与补回或扣分。只有实际登记了 X版写法才拿得到比对基准，而且只有译文使用该 X版写法才算译出；网翻/台版只在 X版已登记时作为“旧写法，不要回改”的对照。真正的空值仍是未登记，只能作为"这一句可能是谁在说"的线索——备注写的是说明，不是译文里该出现的东西，拿它比对只会每行都报流失。
- **判定单位是章或卷，不是行**——一行台词往往看不出说话人，但一章里出现了某角色的人名，他的说话习惯就很可能出现在这一章的台词里。程序按章节名分组，用「人名命中」确定该章出现的角色（只命中姓氏之类的片段只作提示，不启用规则），并按 `小说首次出现` 的卷号过滤掉本卷不可能登场的角色。
- **章级判定在构建工作台时算一次并落盘**（写进 `translation-compare.json` 的 `speechHabits` 顶层块，同时嵌进页面）：可复现、可审计，页面上能直接看到"本卷几章命中、哪些行疑似说话特色流失"（这些行会带「特色流失」标记），AI 任务跑多次也不用重算，离线脚本读到的是同一份结论。**注入到某一行的规则会再按行收窄**：只有"这一行提到了该角色"或"这一行原文出现了他的口癖"的角色条目会进这一行的提示词，其余行不背别人的规则；页面上显示的角色与流失结论仍是章级的，不受收窄影响。
- **行级的说话人判断在 AI 校对时进行**：出现说话习惯特征的行，先让模型判断这一行是谁在说话（结果写进备注的「说话人：」一行，便于人工核对），确认是候选角色才按他的习惯判断；确认不了就不据此判缺陷，也不硬套口癖。
- 原文有口癖、译文完全没体现时，判为说话特色流失，给出把特色补回的最小改动；只有类型可靠（第一人称/接续词/句首句末语气词/谓语形式）、本项目登记了实际写法、且位置正确（句末语气词必须在句末，后接标点、引号、行尾或 ☆ 这类装饰符号；单字汉字口癖如「力」「超」必须落在词首——否则风カ/火力/磁力/能力这类普通词会到处误命中）才提示。中日同形的既有写法（如「力」→「力」）不参与流失检测，但会在角色已由名字或其它口癖确认后作为锁定规则注入，防止模型把它当错字删掉。`-` 条目只注入“不作特殊处理，也不得采用网翻版或台版写法”的硬约束；真正的空值条目只作"这句可能是谁在说"的线索。两者都不能拿来判译文缺漏。
- 落盘块带**表指纹**：表在构建之后被改过时，AI 任务会按最新表重算并在日志里提示"重新构建工作台可让页面同步"，不会拿旧结论又不说。

`--by volume` 可切换成整卷口径。

### 用日文原文校验

index-X 缓存的日文原文（`<index-X>/.cache/epub-work/japanese-text/[S3_01]…`）可以校验对齐产物与上述判定，加 `--verify-source` 即可（目录缺省取同级 `../index-X`，或用环境变量 `INDEX_X_DIR` / `--index-x` 指定）：

```powershell
node scripts/speech-habit.js --profile demo --verify-source
```

校验三件事：卷目录与正文文件是否齐全；快照里的章节能否与原文的「序章 / 行间N / 第N章 / 终章」结构标记一一对应（中日章名是翻译关系，只比结构标记）；各角色口癖在原文与快照 `jp` 列里的出现次数——差值为 0 说明对齐产物完整，偏少通常是后记、插页没有收入正文，明显缺失则说明快照丢了内容，会影响说话习惯与补回判定。

## 校对写回

写回自动备份为可选项，与项目绑定，默认关闭。可在工作台「修改结果」操作区勾选「写回自动备份」（或在控制台写回选项中设置）；开启时在每次实际写入前都会在被修改文件旁保存备份：首次为「原文件名.bak」，之后为「原文件名.时间戳-随机标识.bak」，已有备份不会被覆盖或自动删除。EPUB 压缩文件备份整本；解压目录只备份被修改的正文文件。备份失败会停止本次写入。恢复时请先停止写回，再将所需备份复制回原路径；确认无须恢复后可自行清理备份。

同一控制台服务内，对同一目标的文本写回和说话人标注会依次执行，避免并发覆盖。

翻译写回会核对页面所属项目和内容版本。切换项目后，旧页面的写回会被拒绝；请切回对应项目并重新打开页面。只应用新布局、内容未变化时仍可写回。

翻译比较工作台的「写回」可以把勾选的修改结果写回原文件，说话人归属工作台也可以把说话人标记写回原文件。翻译写回支持 UTF-8 TXT、XHTML/HTML、EPUB 文件和单本解压的 EPUB 目录；说话人标注支持后三种带段落标签的格式。TXT 按空行定位完整段落，保留未修改内容、BOM、段首缩进和原有换行格式。

写回总是修改输入选择中登记的原始路径（通过控制台的系统选择窗口登记，窗口不可用时粘贴本机路径），与 git diff 立即可见；早期版本遗留的浏览器上传导入副本仍可读写，写回会如实提示目标是导入副本。写入按行文本在原文件中定位段落，含 ruby 注音等内联标记的段落会整段替换并保留内联标记，多段合并行允许跨 XHTML 文档。「单行写回」写回并确认该行，「批量写回 / 批量确认」作用于当前筛选结果，「确认自动不改」则直接确认全书中 AI 判断无需修改的条目（无视当前筛选）。

定位按**整卷行序**做：页面会把目标列每一行的文本随请求一起发出，写回从卷首按行序把每一行落到原文件里它自己那一段上。所以同一段文字在一卷里出现多次时（例如两处独立成行的 `<p>尽管如此。</p>`），第 2 处就落到第 2 处，不会因为第 1 处先出现而被改掉。

写回只认**唯一且位置对得上**的那一段，落不到实处就宁可不写，并把这一行原样留给你复核：

- **定位失败的行不写入**（`missed`）。最常见的原因是页面快照生成之后源文件被改过——页面上那一行还持有旧文本，而原文件里那一段已经不在了。这种情况下写回不会「再往前找找」，因为同一段文字在别的章里出现时，那样做会把这一行的内容写到别的段落甚至别的文件上。
- **有多处同段的行不写入**（`ambiguous`）。同一段文字在附近出现两次时无从判断该改哪一处（对话里的「「……」」这类短句最容易撞上），写回会跳过并说明原因。
- **前面有同一段文字的行没能落地时也不写入**。这种情况说明页面与源文件已经不同步（前一行在原文件里找不到），原文件里那一处到底属于哪一行无从判断，写回会把后一行也停下来交给你复核。
- 这些未写入的行**不会**被标记为「已确认」，仍留在复核视野里；写回结果会分别报出条数。


### 备注与找回

备注和人工确认保存在浏览器本地，每条已核验记录带有所在行的内容签名。本地存储按来源隔离：不同浏览器、浏览器配置档、端口，以及直接双击打开的 `file://` 页面，各持一份互不可见的备注。

首次打开尚未保存过的空间时，页面只在本项目的历史空间内按行集或唯一行签名自动找回记录；换成另一对输入文件后，旧项目不会参与自动扫描，只保留在「备注空间与找回」列表中供你手动预览。已有记录（包括刻意清空的空间）不会自动搬入旧数据。「应用新布局」只更新页面，不改变行集和备注空间键。同一行在多份历史空间里记录不同时，页面按行内容签名**逐字段合并**（人工确认保留，另一份记录的分析内容并入分析栏），不再因为「记录不一样」整条放弃——确认预筛这类没有修改结果文本的记录，正是靠这一条在重新生成工作台后被保住。重新生成后若记录或人工确认还是少了一截（内容重复的短行、写回过的行最容易中招），页面会在下次载入时自己补一次：行号与正文都没变的行照搬回来，记录里的「修改结果」就是这一行现在正文的行直接恢复人工确认。

「备注空间与找回」面板把本页记录与历史空间分开。「预览找回」可检查内容匹配、需核验、本页已有、已合并、未匹配的数量及样例，找回只补充空缺行，保留本页已有记录（本页已有记录的行若在历史空间里带人工确认，同样按签名合并）。没有完整行签名的旧记录可用至少三个唯一修订文本锚点推断行序，或在空间详情中「按行号找回」。只剩行序推断的条目会标记为「未校验」，不计入人工确认，写回与批量确认会跳过；而记录里的「修改结果」与这一行现在的正文逐字相同时，说明那是你批准并写回的成品，直接按已确认处理；点行内「未校验」只解除这一行的写回隔离，不会自动勾选人工确认，因此它仍留在「未人工确认」筛选里，可以直接写回。只有写回成功或单独勾选人工确认，才把这一行算作人工完成。面板提供「清空本页」和「清空历史」，清空前会要求确认，且不会误删另一类空间。

「导出本页」与「备份全部」均导出可重新导入的 JSON，包含尚未保存到本地的编辑。导入兼容旧版单空间及全空间备份；重复内容跳过，同名但内容不同的记录保存为副本，再由你预览找回。存储写满时保留来源空间和页面内存，可导出后手动清理已备份的历史空间再重试保存；发现当前空间损坏或被其他页面修改时暂停保存，避免覆盖。

## 常见问题

- **Pandoc 未安装**：运行 `npm run check:pandoc`，或设置 `PANDOC_BIN`。
- **确认信息像是被清空了**：备注只存在浏览器本地，并按「项目标识 + 行集签名」分区保存；重新对齐或更换导入方式会换到新分区，新页面读到的是空分区。原分区不会被删除，按上节「备注与找回」找回或导出导入即可；若各分区都对不上，先去当时那个浏览器、配置档或 `file://` 页面导出，再回到这里导入。
- **写回落到了同一段文字的另一处**：页面脚本是构建期内嵌的，老页面仍用老定位逻辑。先重新生成工作台（或在控制台重新导入后生成）再写回；写回本身只改它定位到的那一段，落不到实处会报「定位失败」或「有多处同段」并且不标记为已确认。
- **直接双击 HTML**：可以查看静态结果，但输入导入、写回、项目切换和 AI 校对需要通过 `npm run setup` 启动本地服务；本地服务只接受由它自己提供的同源页面发起这些操作。
